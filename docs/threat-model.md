2. **The root check decides the run's mode, and exit code 3 has a producer.** `require_root` is `src/apply.rs:57`; the run calls it to choose between the `--list`, recommend and write modes (`src/main.rs:544`, `decide` at `src/main.rs:110`) and the writer calls it again on its own entry point (`src/apply.rs:307`), so the mode decision and the writer cannot disagree about what root is. The non-root write path returns 3 after printing the `sudo` line (`src/main.rs:837`), and `main` passes whatever code `run()` returns straight through (`src/main.rs:1151–1157`).

5. **The only environment variable the code consumes is `TMPDIR`,** indirectly, through `std::env::temp_dir()` in `private_temp_dir` (`src/verify.rs:54`). `HOME`, `PATH`, and `XDG_*` are never read. `std::env::args()` is the CLI source (`src/main.rs:45`). A second consumer is planned and does not exist yet: `LC_ALL`, else `LANG`, read once at startup to choose the language the run prints in and for nothing else (`SPEC.md` Localization, `ROADMAP.md` D28a). When it lands, this fact reads "`TMPDIR`, `LC_ALL`, `LANG`" and the locale is display text that no module reached from `src/apply.rs` may read.

7. **The freshness `Date` has a strict and a tolerant parse.** `fresh::release_date` reads `Date:` only inside the cleartext-signed region and refuses any body whose preamble is not whitespace-only (`src/fresh.rs:103–129`); `fresh::release_date_tolerant` keeps the whole-body scan that display and ranking use (`src/fresh.rs:131–143`). The probe keeps both: `updates_date` for lag and the table, `signed_updates_date` only when the strict parse succeeded (`src/fresh.rs:155–190`).
8. **The write baseline is a value, and only the verifier mints it.** `Probed` carries the verifier's value in a `verified_updates` field (`src/fresh.rs:175`) and `Reference` carries one in the same field (`src/probe.rs:74`); `write_baseline` takes the canonical reference when that value is `Some` and otherwise the newest verified candidate, `None` when nothing verified (`src/main.rs:1067`), so a write fails closed. Notes that change what a control must do:

- A4 is not a "malicious mirror" only. `mirrors.ubuntu.com` is plain HTTP (`SPEC.md` Pipeline step 3.2), and candidate URLs from that source are marked unverified today. Any host that wins the ranking becomes an apt URI: `apt` will then fetch `Packages` and `.deb` files from it and verify them against `Signed-By`, so package content stays authenticated, but *which* server the machine trusts the availability of is chosen by ranking.
- A5/A6 do not authorize installation. Even a forged `Date` cannot install a package: `apt` still checks archive signatures. What A6 buys an attacker is the position of the *selected* mirror, which is then written to `/etc/apt`. That is the whole weight of D6f P1 #1 — see 3.9.
- A2 is the one input with a second consumer planned. `LC_ALL` and `LANG` choose the language a run prints in, and nothing else: the value must be resolved once at startup, before any apt file is opened, must be normalized and matched against the tags the binary carries, and must reach no path, decision, comparison, ordering, plan, written byte or exit code, and no module under `src/apply.rs` may read it. `SPEC.md` Localization states the rule and `ROADMAP.md` D28c carries the container pair that proves a root write is identical under `LANG=C` and under a shipped locale. The table's "entry point today" column still names only `src/verify.rs:54`, because the read does not exist yet.
- A11 matters most where a directory is created on first use. The old `SPEC.md` Errors and self-healing rule created missing own directories with `create_dir_all`, which succeeds on a directory another user already created; the rule now covers the cache directory only, and the backup root fails closed instead (7.6).

## 3. Trust boundaries and controls

Each boundary lists what exists with `file:line`, then what is missing and what the code does instead. "Missing" means: if D9 were written today on top of this code, that input would reach a write unprotected.

### B1 — Arguments and environment → program

Existing:
- Country is uppercased and shape-checked before any lookup (`src/main.rs:51–62`); unknown codes are rejected against the Launchpad country table before any network call (`src/main.rs:81–94`, wired at `src/main.rs:96`).
- Architecture and country are validated in preflight before geolocation or HTTP (`src/main.rs:95–107`).
- Unknown options are hard errors (`src/main.rs:75`).
- `gpgv` runs with `env_clear()` plus `LC_ALL=C` (`src/verify.rs:156–158`), so A2 cannot reach the verifier.

Missing:
- No `geteuid` check and no exit-3 path, so nothing today distinguishes a privileged run.
- Nothing validates `TMPDIR`: `private_temp_dir` joins it to a random name and creates that directory 0700, but the parent is never checked for owner, mode, or sticky bit, and a `TMPDIR` on a world-writable mount is accepted. `SPEC.md` Freshness trust boundary claims "a private 0700 temporary directory"; the directory is private, the parent is untrusted. Already recorded as a D6f P2.
- Nothing clears the environment for the *program*, only for the verifier. A root run must build its own minimal environment rather than inherit one, with one exception that changes no decision: the display-only locale read of `LC_ALL`/`LANG` that `SPEC.md` Localization requires, resolved once before any apt file is opened and never reached from a module `src/apply.rs` uses (the bullet below, and Appendix A item 13).
- The locale read that D28a adds is the second consumer of A2 and must stay display-only: resolved once before the pipeline, never reached from a module `src/apply.rs` uses, and never a path, a decision, a comparison or a sort key. `SPEC.md` Localization states the rule; section 2's A2 note and D29a's four-way root-write pair are where it is checked — D28c's pair is a determinism check and cannot discriminate until a translated catalog ships.

Required before D9: the write requires uid 0, a non-root run writes nothing and exits 3 with the `sudo` line, no environment variable reaches a decision the write makes — the only read the program makes at all is the display-only locale read above — and passes a constructed environment to any child.

### B2 — apt source contents → inventory

Existing:
- The root directory is refused unless `symlink_metadata` reports a directory (`src/sources.rs:383–405`).
- `/etc/apt/sources.list` is accepted only when `symlink_metadata` says regular file (`src/sources.rs:409–421`); the same for `sources.list.d` (`src/sources.rs:423–425`, refusal at `src/sources.rs:479–483`).
- Only `.list` and `.sources` are read; other names are reported and skipped (`src/sources.rs:444–456`).
- Directory entries are filtered on `entry.file_type()` (`src/sources.rs:458–466`), which does not follow symlinks.
- Non-UTF-8 files are reported and skipped, never guessed (`src/sources.rs:497–503`).

Missing:
- No ownership or mode check. A file owned by uid 1000 with mode 0666 under `/etc/apt/sources.list.d/` is inventoried and, in a later milestone, would be rewritten by root. The code reads whatever is there.
- No TOCTOU resistance: `symlink_metadata`/`file_type` checks at `src/sources.rs:410` and `src/sources.rs:458` are separate syscalls from the `std::fs::read(&path)` at `src/sources.rs:492`, which re-opens by name and therefore follows a symlink substituted in between. A local attacker who can replace the entry wins a root read of any root-readable file, whose content then lands in the plan and in `/etc/apt` (world-readable). Std-only fix without a new dependency: open with `OpenOptions`, then compare `File::metadata()?` `dev`/`ino` (`std::os::unix::fs::MetadataExt`) against the `symlink_metadata` result, and use the open handle for the read. `libc::O_NOFOLLOW` is not available without a new dependency.

Required before D9: the root run opens every target with the identity check above, and aborts on any change.

### B3 — Network responses → candidates, dates, signatures

Existing:
- One 10 s budget per call, not per hop (`src/http.rs:12`, `src/http.rs:98`, `src/http.rs:152–160`).
- Redirects followed by hand, every hop re-validated (`src/http.rs:99`, `src/http.rs:150`), at most 3 (`src/http.rs:17`), `https`→`http` downgrade refused (`src/http.rs:189–195`), protocol-relative and relative `Location` refused (`src/http.rs:128–142`).
- Proxies explicitly disabled so the environment cannot reroute traffic (`src/http.rs:101`).
- Private, loopback, and link-local addresses filtered at resolution, on the exact addresses connected to (`src/http.rs:68–92`, `src/mirrors.rs:211`).
- Size caps: 2 MiB pages, 256 KiB small files (`src/http.rs:14–16`), 512 KiB for `InRelease` (`src/probe.rs:13`, `src/verify.rs:19`), 4 KiB for the informational `-security` head (`src/probe.rs:15`), 1 MiB sample (`src/probe.rs:16`).
- `Verified` requires exit success, `GOODSIG`, `VALIDSIG`, and no `BADSIG`/`ERRSIG`/`NO_PUBKEY` (`src/verify.rs:250–257`).

Missing:
- A6: closed by D6f — the write path takes `signed_updates_date`, display keeps the tolerant parse (3.9).
- No verified-plan type: `VerifiedDate` exists (3.10), the plan-level gate is D9's (G2).
- The throughput sample is attacker-controlled: only the xz magic and a 64 KiB minimum are checked (`src/probe.rs:18`, `src/probe.rs:153–156`). A mirror that streams 1 MiB of zeros at line rate wins the speed tie-break and can win the group. Accepted risk with a stated reason: throughput cannot be verified from the outside, `SPEC.md` Pipeline step 9 already treats it as relative, and the loser of that lie is a slow mirror, not an unauthenticated package.
- The `-security` head is unverified by design (`src/probe.rs:89–97`, `SPEC.md` Freshness trust boundary). Nothing may consume it for a write; today it feeds only display.

### B4 — Selected mirror URL → rewrite plan

Existing:
- `rewrite_source` re-validates the selected URI before planning (`src/sources.rs:800–807`).
- `validate_url` enforces `http`/`https` only, no backslash, no `@`, no whitespace or control characters, ≤2048 bytes, valid port, bracketed IPv6 parsed, local names rejected, numeric private hosts rejected (`src/mirrors.rs:247–324`, `src/mirrors.rs:161–211`).

Missing:
- Nothing ties the selected URI back to the candidate set that was actually probed. A byte-identical plan can be produced from a URI that appeared in no mirror list, because `rewrite_source` validates shape only.
- Nothing requires the selected URI's `-updates` `InRelease` to have been `Verified` in the same run. `fresh::Probed` has no field for it (finding 8).
- Nothing restricts the URI host to a *public resolvable* host at plan time. Resolution happens in the prober (`src/http.rs:70–92`), so a candidate's DNS answer can differ between probe and write. This is bounded: the write phase does not connect to the host, it only writes the string.

Required before D9: the plan carries the URI, the digest of the candidate it came from, and a verification proof minted by the verification pass in the same process; the root run accepts nothing else.

### B5 — Backup directory and manifest → root read-back and restore

Existing: nothing. There is no backup code, no manifest format, and no `--restore`.

What exists nearby: `SPEC.md` Apply requires mode 0700, refusal of a symlinked directory, a manifest of original paths, and aborting the whole apply on any backup failure; `SPEC.md` Apply requires `--restore` to validate that every manifest path is under `/etc/apt/` and a regular file after resolution.

Missing, and required before D9:
- The backup root must be verified after creation: `symlink_metadata` says directory, `uid == 0`, mode exactly 0700, and the path is not a symlink. A pre-created `/var/backups/apt-scout` by uid 1000 must be a hard abort, not a `create_dir_all` no-op. `SPEC.md` Errors and self-healing now states that exception (Appendix A item 6): the `create_dir_all` self-heal covers the cache directory only.
- The manifest must be written by root, mode 0600, and read back with the dev/ino identity check of B2.
- The manifest must not be able to name a path. It carries a target *identifier* from a closed enum plus a file name validated against `[A-Za-z0-9._-]{1,64}` with a `.list`/`.sources` suffix; the path is then built as `/etc/apt/sources.list` or `/etc/apt/sources.list.d/<name>`. Containment is by construction, not by string prefix checking.
- Each record must carry the original digest, mode, and owner so a restore can prove it is restoring what it backed up, and refuse otherwise.

### B6 — No boundary crossing (removed)

The plan handed from one process to a root process, which this entry used to describe, was removed on 2026-11-12 with the CLI ruling: no plan, file, or stdin message crosses a process boundary, so there is no producer of untrusted plan bytes to defend against. The checks that remain are listed in section 5. See 7.2.

### B7 — Terminal input (TUI, D13+)

Existing: no TUI, no `ratatui` dependency (`Cargo.toml`), so the surface does not exist yet.

What the design imposes now so D13 does not have to revisit it:
- A keystroke is authorization for exactly one thing: the confirm step. It never carries data.
- Custom mirror URLs typed in the TUI (`SPEC.md` Apply, Custom URLs) are input A4: they are validated and probed before the plan is built and reach it only through B4's re-validation.
- Nothing that root prints may contain unescaped mirror-controlled bytes. A mirror's URL, `Origin`, `Label`, or error text can contain `ESC`; printing it as root into a shared terminal is a control-sequence injection into the user's terminal. The root run must render untrusted strings with control characters replaced. Nothing does this today (`src/main.rs:311–340` prints URLs raw): the mitigation belongs to D13, and the exposure until then is a read-only table printed by a root run that writes nothing.

### B8 — A hostile local user writing where the program reads

Existing:
- The verification temp name is 8 random bytes plus the pid, created `create_new` and mode 0600, in a directory created 0700 (`src/verify.rs:49–66`, `src/verify.rs:129–149`), so a pre-created file or directory at that path causes a clean `Unavailable`.

Missing:
- The temp parent is `env::temp_dir()` (`src/verify.rs:54`) with no owner/mode/sticky check.
- Any future backup or plan directory created on first use is not verified after creation (B5).
- `system-security.sources` creation must be `create_new` (exclusive), never overwrite: the enum discriminator already exists (`src/sources.rs:39`), no code uses it.

### 3.9 D6f P1 #1 — a write may use only a `Date` from inside the signed region

What the code does: `fresh::release_date` accepts a body only when nothing but whitespace-only lines precedes a line that is exactly `-----BEGIN PGP SIGNED MESSAGE-----`, skips the armour headers to the first blank line, and reads `Date:` before `-----BEGIN PGP SIGNATURE-----` (`src/fresh.rs:103–129`). `fresh::release_date_tolerant` keeps the whole-body scan for display and ranking (`src/fresh.rs:131–143`), and the probe carries both values (`src/fresh.rs:155–190`). Why the rule exists: `gpgv` ignores everything before the armour, so a mirror can prepend `Date: <chosen>` to a genuinely signed body and the signature still verifies; the status stays `verified`, and only the parser separates a signed date from a displayed one.

Ruling: **for a write, the date must come from inside the cleartext-signed region, and the region must be located by the parser, not by the verifier.**

Required behavior, both sides:
- Only whitespace-only lines may precede `-----BEGIN PGP SIGNED MESSAGE-----`, and the armour line must start its own line. A body with any other prefix is **not** `Invalid`: `gpgv` verifies it and the status stays `verified`, because the prefix is outside what the signature covers, not something that breaks it. What such a body cannot supply is a trusted `Date`, so a write may not use it, while read-only ranking keeps displaying and ranking that date under the `SPEC.md` Freshness trust boundary sentence ("ranking may display and use an `InRelease` `Date` even when signature verification is `invalid` or `unavailable`").
- The `Date:` header is taken from the cleartext between the armour headers (after the `Hash:` line) and `-----BEGIN PGP SIGNATURE-----`. A `Date:` occurring after the signature block is not the release date.
- A write requires: parse succeeded inside the signed region *and* `SignatureStatus::Verified`. Both facts travel together (section 5), so no later code can combine one without the other.
- Regression fixture: `tests/fixtures/signed/noble-updates-InRelease.prefixed` — the existing fixture with a forged `Date:` prepended — must produce a date equal to the genuine one for a write, or an outright refusal; it must never produce the forged date. The hand proof in D6f (`gpgv` exits 0 with `GOODSIG`/`VALIDSIG` on the prefixed copy) is the reason this test is mandatory.

What this meant for a write, and why it blocked D9 rather than merely degrading read-only output: without it, every other control in this document inherited a forgeable input. D6f implemented it (PR #29); 7.4 records the decision.

### 3.10 D6f P1 #2 — the write baseline is a verified value

What the code does: `Probed` carries the verifier's value in a `verified_updates: Option<VerifiedDate>` field (`src/fresh.rs:175`) and `Reference` carries one in the same field (`src/probe.rs:74`), so the date and the signature status travel as one value instead of in parts a caller can recombine; the baseline is the canonical reference when that value is `Some`, otherwise the newest candidate that carries one, and absent when nothing verified, so the write fails closed (`src/main.rs:1067`). The proof is unforgeable now: `SignatureStatus::Verified` carries a `VerifiedProof` whose single field is private to `src/verify.rs` (`src/verify.rs:35`), `region_date` builds a `VerifiedDate` from the bytes `gpgv` accepted and nowhere else (`src/verify.rs:112`), the one stand-in the tests and the write harness use calls it and is compiled out of every shipped build (`src/verify.rs:121`), and `the_write_proof_is_minted_only_in_the_verifier` (`src/verify.rs:624`) scans `src/` for a second mint site. The verified-plan half is `Plan`, which holds the proof beside the URI and the bytes it was issued for (`src/plan.rs:109`, `src/plan.rs:121`).

Ruling: **"verified" must be a value, not a string and not a bool, and the write gate must be able to accept only that value.**

Required behavior:
- One constructor produces the proof: the verification pass itself, in the same run, before the write. `SignatureStatus::Verified` becomes unconstructible outside `verify` (private module constructor; `is_verified()` stays for display).
- The proof carries the parsed date and the fact that the date came from the signed region (3.9), so the two P1s close into a single value that cannot be assembled from parts.
- `fresh::Probed` carries the proof's status, and the baseline is `Verified(date)` or absent. `fallback_baseline` contributes a date only from candidates whose `-updates` `InRelease` was verified in this run. A forged future date is then impossible rather than merely implausible: a genuine Ubuntu signature cannot cover an attacker's `Date`.
- If no candidate verifies, the write fails closed with an explanation naming the cause (missing `gpgv`, missing keyring, every mirror `invalid`), and read-only output is unchanged.

What this meant for a write, and why it blocked D9: the accepted rule in `SPEC.md` Freshness trust boundary ("the selected mirror's `-updates` `InRelease` and the canonical reference used as freshness baseline must both be `Verified`") had no representation, so it could not be enforced by construction. D6f implemented the baseline half (PR #29) and 7.5 records the decision; the plan-level half is `Plan`, which carries the proof beside the bytes it was issued for (`src/plan.rs:109`), and D25 closed the half that stayed forgeable until PR #43, which is what the paragraph above now states in the present tense.

## 4. Self-reexec: the explicit decision

### 4.1 The constraint that decides it

A process cannot obtain privilege for itself, so "self-reexec" is shorthand for one of three mechanisms, and they are not equivalent:

1. exec itself under `sudo` — the program invokes `sudo`. Forbidden by `AGENTS.md:108` (`Privilege-security gates`: "Never add or assume `sudo` self-reexec is safe") and by `SPEC.md` Privilege boundary bullet 4, which states that the program never re-execs itself privileged and never invokes `sudo`. The ban stands in the ruled design: a program that execs `sudo` converts every path it controls into a root path, and inherits `sudo`'s environment policy as its only defense.
2. install a setuid-root bit — the binary becomes a local privilege-escalation candidate by definition. Any local user can run the write phase. The only thing standing between them and root file writes is the program's own validation of an input that the same local user supplies.
3. ask the user to run the second phase as root — the mechanism the user's own `sudo` provides, with no privilege manufactured by the program. This is the ruling (7.1).

Mechanism 3 is the ruling (7.1); mechanisms 1 and 2 are the rejected forms analysed in 4.3 and 4.4. The question D6e answered is what the second, root-only invocation is allowed to contain, and the answer is section 5: a plan, and nothing else. That answer governed a two-process design that the user later removed (7.2). The one-shot modes — `sudo apt-scout`, `sudo apt-scout --tui`, `sudo apt-scout --restore` — are also mechanism 3, because the user's own `sudo` supplies the privilege, but they parse untrusted input in the root process, and `SPEC.md` CLI and Privilege boundary state that cost plainly instead of presenting the one-shot run as isolated.

### 4.2 The ruling — no self-reexec: refuse and print the exact command

The program never execs anything privileged. A non-root run writes nothing, prints the `sudo` line and exits 3. The write is one code path in the same process (section 5): it builds a plan, validates it against the closed target enumeration and the on-disk digests, verifies the selected mirror's `InRelease`, and only then writes. In a root run the networked discovery therefore happens in the root process as well; `SPEC.md` Privilege boundary states that cost and names a two-process split as future work, not as a supported flag.

- **Buys:** no setuid bit, no internal `sudo`, no second executable to package; privilege comes only from the user typing `sudo`; the write is bound to the bytes the run validated against the disk; no plan format, transport or producer metadata exists to secure, because nothing crosses a process boundary.
- **Costs:** the root process parses untrusted network responses before it writes. The defence is the order of operations — verify the `InRelease`, validate the plan against the disk, then write — not isolation. A split that keeps the network phase out of root is future work (4.4, 4.6).
- **How it fails:** visibly. Wrong uid → exit 3 with the `sudo` line, no file opened for writing. Failed validation → exit 1 with the failing field or path, nothing written. No partial state is reachable, because the writer validates the whole plan before opening any target.
- **What an attacker gains:** nothing through the write path that a local user who may run `sudo apt-scout` does not already have. What the validation bounds is *which* bytes root writes: only the enumerated targets, only the bytes the run validated, and only over a disk state whose digests still agree (5).
- **Testable in disposable containers:** fully. `docker run` as root exercises the write; the refusal case runs as uid 1000; a failing validation is injected with a test hook. No setuid and no nested privilege boundary to simulate.

### 4.3 Rejected — self-reexec through a fixed absolute path, minimal environment, pre-write confirmation token

The program re-execs `/proc/self/exe` (absolute, not `PATH`-derived) with a cleared environment, passing the plan over an inherited fd and a token that the second phase requires before writing.

- **Buys:** one command for the user. A minimal environment makes A2 explicit rather than inherited. A token makes a stale or replayed invocation fail.
- **Costs:** the privilege still has to come from somewhere. Without `sudo` inside the program and without a setuid bit, the re-exec runs at the same uid as the parent, so nothing is gained; with the setuid bit, the audit surface is a setuid root binary that reads a plan from an unprivileged writer. That combination is the classic local-root pattern, and the token does not change it: a token the unprivileged caller generates is not a MAC, and if the root phase generates it, the caller never sees it. So Option B is either Option A with extra machinery or a setuid binary.
- **How it fails:** opaquely, which is the worse problem. A re-exec under an unexpected uid, a `/proc/self/exe` that reports `(deleted)` because the package was upgraded mid-run, an environment that `sudo` rewrote — each produces a failure in a process the user did not start and cannot inspect from the command line.
- **What an attacker gains:** in the setuid form, everything: a local user runs the write phase, and the plan they supply is validated only by code they can read and probe. In the non-setuid form, nothing beyond Option A, at the cost of a second code path.
- **Testable:** partly. The non-setuid paths are testable; the setuid path needs a container with a setuid install step, and the interesting failures (deleted exe, environment rewrite) are the ones that are hardest to reproduce deterministically.

### 4.4 Deferred — privileged helper process spawned once with a validated plan

The root-run process spawns one child (or ships one second binary) that owns every privileged operation and links nothing but `std`.

Two forms, and only one is compatible with the ruling:
- **C-spawned-by-root:** the user runs the write mode as root; it forks a child that reads the plan from a pipe and performs the writes. If the second binary is separate, it contains no `ureq`, no `gpgv` spawn, no TUI, no DNS — the privileged image is a few hundred lines and its interface is a byte schema. Out for v1: this is not an option held in reserve, and reintroducing it is a new product decision by the user (4.6, G3).
- **C-setuid-helper:** the unprivileged parent spawns a setuid helper. Same rejection as Option B: it manufactures privilege from an unprivileged caller.

- **Buys:** structural isolation that a reviewer can see in the dependency graph rather than having to trust a discipline. The interface between the two halves is enforced by the OS, and the privileged binary's "does not make network requests" claim becomes checkable (`cargo tree` on a two-crate workspace) instead of checkable-by-grep.
- **Costs:** a second binary in `.deb` assets (`Cargo.toml` `package.metadata.deb.assets`, currently one entry) and in the release tarball, a workspace split or a feature-gated second `[[bin]]`, and two artifacts to keep in version lockstep (the plan carries a format version for that reason). It also doubles the amount of packaging and release surface tested before D9.
- **How it fails:** like Option A, plus one new failure: a version skew between the two binaries. Mitigated by requiring an exact plan-format version match and refusing otherwise.
- **What an attacker gains:** nothing beyond Option A. The helper is reachable only from root.
- **Testable:** fully, in the same containers; the container test must additionally assert that the privileged binary contains no network-capable dependency, which is a stronger and cheaper claim to verify than a grep review.

### 4.5 Ruling and reason

**Option A. DECIDED 2026-11-12 by the user (via the parent orchestrator). The writer is one binary and one code path, and a split into a separate privileged artifact is out of scope for v1 (4.6, G3).** Specifically: no self-reexec anywhere in the codebase; a non-root run writes nothing, exits 3 and prints the `sudo` line; the write validates the plan it built against the closed target enumeration and the on-disk digests, verifies the mirror's `InRelease`, and only then writes, and the write itself makes no network request, runs no external process, invokes no shell, and resolves no command through `PATH`. Amended 2026-11-12 by the user (via the parent orchestrator) with the final CLI ruling: the two-step plan split flags are removed from the product (7.2) because the feature is one action, and the plan is internal (section 5). The option choice itself — no self-reexec, one binary — is unchanged.

Reasoning, in order of weight:
1. It is the only option that provides privilege without manufacturing it. Options B and C do not give the program anything the user's own `sudo` does not, and they add code that pretends to.
2. The security property that matters is not "a second process" but "validated bytes over a disk state that still matches". A two-process split would buy isolation of *code*, not of *authority*, and it costs a plan format, a transport and a producer rule — three mechanisms that exist only because a plan crosses a boundary.
3. Fewer concepts: one binary, one code path, one validation, one test matrix. A split's wire format, decoder and producer metadata exist to solve a problem the one-process design does not have.
4. Testability: the refusal, the validation and the write are all reachable from a container command line, with no setuid install step and no nested privilege transition to reason about.

### 4.6 One binary, and the triggers that remain

- **One binary — decided, not a threshold.** The program is one binary: the writer is one code path in the same executable, and a separate privileged artifact is out of scope for v1. Nothing in this record reopens that — not a size measurement, not the shape of `src/apply.rs`, not a code review finding (G3). A future split of the write path into a second artifact or a second process would be a new product decision taken by the user, with the threat model 4.4 describes; it is not something a threshold triggers and not a decision an agent may take, summarize or argue from a line count.
- **The user-facing cost was settled on 2026-11-12 by the user.** The workflow is one command, `sudo apt-scout`; the networked discovery runs in that root process, and `SPEC.md` Privilege boundary states it plainly instead of presenting a split as equivalent. A two-process split stays future work (4.4); the record keeps the analysis, not a flag.
- If a future distribution requirement forces a setuid or polkit integration (a GUI, or a non-terminal apply), the analysis in 4.3 and 4.4 applies unchanged: that path needs its own threat model and its own D6e-equivalent decision. It is out of scope for v1, which is a terminal tool.
- If a future requirement brings a split back (4.4), the transport question returns with it. There is no transport today: 7.2 records why.

## 5. Write validation (in-process)

The program is one process and one code path. Discovery, verification, ranking, rewrite planning and the confirmation produce a plan in memory; the plan is validated against the closed target enumeration and the current on-disk state; only then does the first byte change. No plan leaves the process, so there is no wire format to decode, no producer metadata to check and no transport to secure: 7.2, 7.3 and 7.9 are removed with that boundary.

What the write validates before its first byte, and why each check exists:

- **Targets come from a closed enumeration.** `Target` is `SourcesList` or `SourcesListD(FileName)` (`src/plan.rs:27`), and `FileName` is validated by `SourceName::parse` against `^[A-Za-z0-9._-]{1,64}$` plus `.list`/`.sources` (`src/plan.rs:36`), so no path string can name anything outside `/etc/apt` and no prefix comparison has to be trusted; `Target::parse` accepts those two spellings and nothing else (`src/plan.rs:60`). S3, S11.
- **Each target is re-checked at open time.** `capture` re-reads every target through `read_state` (`src/apply.rs:429`, `src/apply.rs:967`) and `check_one` refuses it (`src/apply.rs:500`): a regular file after `symlink_metadata`, never a symlink; mode, owner and the digest of the bytes the plan was computed from are re-read on the opened handle and compared. Any difference aborts before the first write (B2, B8, S5, S6).
- **Every byte is digest-bound.** `Plan` carries each write's bytes with the digest that describes them (`src/plan.rs:116`), and `validate` recomputes the SHA-256 of the new content and refuses unless it matches (`src/plan.rs:146`); no byte reaches a target on a digest that disagrees. S15.
- **Freshness is a value, not a boolean.** `check_freshness` takes the write's `VerifiedDate` (`src/apply.rs:359`), which only `verify::region_date` mints, from the bytes `gpgv` accepted (`src/verify.rs:112`), and which reaches the writer through `Probed.verified_updates` (`src/fresh.rs:175`), for the selected mirror's `-updates` `InRelease` and for the write baseline (3.9, 3.10). If verification is unavailable, the write fails closed. S15.
- **Creation is planned, never incidental.** `create_one` is reached only from the plan's create record (`src/apply.rs:832`, `src/apply.rs:868`): `create_new` is accepted only for `SourcesListD("system-security.sources")` on Pop!_OS, with mode 0600, and `EEXIST` aborts with nothing written (7.8, S17).
- **The order is fixed:** validate every file, back up every file, write every file atomically (temp file in the same directory, fsync, rename). The call order is `run` (`src/apply.rs:325`) into `backup` (`src/apply.rs:548`) and then `write_targets` (`src/apply.rs:803`), which lands each target through `create_temp` (`src/apply.rs:922`), `replace_one` (`src/apply.rs:898`) and `sync_dir` (`src/apply.rs:1037`). A backup failure aborts before the first write, and no target is left half-written. S8, S17.
- **The write performs no network request of its own, spawns no process, invokes no shell, resolves no command through `PATH`, and reads no environment variable.** The write path's whole import block is `src/apply.rs:10–18` — std file, io, unix fs and path, plus `crate::digest`, `crate::fresh`, `crate::manifest`, `crate::plan` and `crate::verify`: no `crate::http`, no `ureq`, no `std::process::Command`. `rg -n 'crate::http|ureq|process::Command|env::' src/apply.rs src/plan.rs src/manifest.rs src/digest.rs` matches only the test module (`src/apply.rs:1101`, inside `#[cfg(test)] mod tests`, `src/apply.rs:1073`), and lines 1–1072 of `src/apply.rs` match nothing at all, which is what makes the sentence true. S14 is the test for it and has no case in the `scripts/docker-test.sh` matrix yet; what the matrix does hold is that every write case starts through `wrun` (`scripts/docker-test.sh:106`), a container with `--network none`, one read-only binary mount and no other mount — a property of the container, not a proof of the absence. Verification runs earlier in the same run through the fixed `/usr/bin/gpgv` with a cleared environment (D6c, `SPEC.md` Freshness trust boundary).

**`--restore` does not exist yet: D10 builds it, and no flag reaches it today.** It must read `/var/backups/apt-scout/<backup id>/MANIFEST` by a path it builds itself, and must abort before parsing a byte unless that path is a regular file owned by root with mode 0600 and not a symlink; only then must it re-derive the target set and every per-target digest from the manifest, comparing each record's digest, mode and owner with the backup copy it names, and refuse on the first disagreement. The manifest is the source of truth for what is restored, so a stale or partial manifest cannot restore a subset of the backup (G1, 7.7, B5, S4, S10).

Why the validation stays even though the plan is internal: it is the only thing that makes "the bytes I confirmed are the bytes written" true against a hostile local user (a last-moment substitution, a symlinked target) and against a forged or stale mirror date. Re-reading `/etc/apt` and acting without comparing to the plan would reopen all three; comparing closes them with one mechanism, and it keeps the property checkable without trusting the discovery phase.

## 6. Security acceptance tests for the write path

What the merged container matrix covers, and what it does not. `scripts/docker-test.sh` binds these S-IDs: S16 to W1/W2/W3, the non-root half of S1 to W5, S5 to W6/W7/W8, S6 to W9, S7 to W10, S8 to W11, S9 to W12/W13/W14, S11 to W15, S15 to W16/W17/W18/W19, and S17 to W20/W21; W22 is the positive path; W4 is the harness self-test. Neither carries an S-ID. S3 runs as the `src/plan.rs` unit tests rather than a container case, and S2 is removed (7.2). S4, S10 and S11's manifest half are D11b's and have no case yet. S12, S13 and S14 have no case at all. Wiring the writer into the CLI arrived with D11a (PR #43): `src/main.rs:839` is the write mode and `src/main.rs:882` is the call, with the non-root half of the same decision returning 3 one arm earlier (`src/main.rs:837`). The root half of S1 has no case under its own ID; the ordering it asserts, validation before the first write, is what W9 (S6) shows by pausing the run between the two. The milestone audit that checks this list against the matrix is D12's.

Checklist for a human reviewer. Every case that exists runs in a disposable Ubuntu container whose own `/etc/apt` is the isolated fixture, with `--network none` where the case permits; S3 is the exception and runs as a unit test, and no case may touch a host path. "Fails when" describes the assertion, so a reviewer can check the test is real.

- **S1 — a non-root run never writes, and a root run validates before it writes.** As uid 1000: exit 3, no file opened for writing, and the message names `sudo apt-scout` with the flags of the run. As root, with a target changed between validation and the open (test hook): exit 1, nothing written, and every `/etc/apt` target digest is identical before and after. *Fails when* the non-root run writes anything or exits 0/1, omits the `sudo` line, or a root run writes before passing the validation.
- **S2 — removed 2026-11-12.** It asserted that the root phase refuses empty, truncated or bad-magic plan input over stdin. No plan crosses a process boundary any more, so there is no decoder to test (7.2); the in-process checks are covered by S1, S3, S6 and S11.
- **S3 — Target enumeration and plan-field hostility.** The plan is built inside the program, so the test drives the validation layer directly instead of a decoding fixture: a target name outside `^[A-Za-z0-9._-]{1,64}$` or not `.list`/`.sources`, `..` and absolute names, a `create_new` target other than `system-security.sources`, `create_new == false` on a file that does not exist, a target that is not a regular file after resolution, and a content digest that does not match the bytes to be written. Every one is refused before any open, with nothing written. *Fails when* one is accepted or produces a path outside `/etc/apt` or outside `/var/backups/apt-scout/<id>/`.
- **S4 — Path traversal in the manifest (`--restore`, D10 scope).** A manifest naming `/etc/shadow`, `../sources.list`, `sources.list.d/../../etc/passwd`, a tuple of `/etc/apt/sources.list` as a symlink, or an absolute path: refused, nothing read, nothing written. *Fails when* the path resolution is done by string prefix alone — prove it by including `/etc/apt/../etc/shadow` and `/etc/aptx/sources.list`.
- **S5 — Symlink target.** `sources.list` and each `.list`/`.sources` are replaced by symlinks to a canary outside `/etc/apt`; and `sources.list.d` itself is a symlink to an attacker directory. Each case: refused with the reason, canary unchanged. *Fails when* the write follows the link.
- **S6 — TOCTOU substitution.** With the plan validated, replace a target between validation and write (test hook: a variant that pauses after validation). Expected: write aborts on the dev/ino or digest mismatch, target unchanged. *Fails when* the write proceeds on the substituted inode.
- **S7 — `:ro` → `:rw` mount.** Run the write against `/etc/apt` mounted read-only: exit 1 with the OS error verbatim, no temp file left behind, backup directory either absent or untouched, and a second run does not treat the leftover as a backup. The read-only root is the container's own rootfs and not a bind mount: W10 runs it through `wro`, which adds `--read-only --tmpfs /tmp` to `wrun` (`scripts/docker-test.sh:110`), against a fixture image frozen by `wfixture` because no setup can run against that rootfs (`scripts/docker-test.sh:391`), with `--tmpfs /var/backups` so the backup phase completes into the tmpfs and the write phase meets `EROFS` at its first temp file (`scripts/docker-test.sh:400`). *Fails when* the error is swallowed or a temp file survives.
- **S8 — Backup failure aborts before any write.** Make the backup directory or the timestamp directory unwritable (mode 0500) and make the first backup write fail; assert the order by digesting every target before and after: all identical, and the program's output names which file failed. *Fails when* one target changed.
- **S9 — Pre-created backup directory.** `/var/backups/apt-scout` owned by uid 1000 or mode 0777 or a symlink: hard abort with the reason, nothing written inside it. *Fails when* `create_dir_all` semantics let it through (the old self-heal rule allowed this; `SPEC.md` Errors and self-healing now requires the abort).
- **S10 — Rollback.** Apply succeeds, then `--restore` from the newest backup: every file byte-identical to the pre-apply fixture (`cmp`, mode, uid/gid), including removal of `system-security.sources` on Pop!_OS. *Fails when* any byte, mode, or owner differs, or the created file survives.
- **S11 — Rejection of paths outside `/etc/apt`.** A target name that would resolve outside the two roots, plus a `--restore` manifest pointing at `/usr/bin/gpgv`: exit 1, message names the offending path, no open for write. *Fails when* the write opens any path outside the closed enum's two roots.
- **S12 — Hostile `PATH`/`HOME`/`TMPDIR`.** Run the write with `PATH=/tmp/evil`, `HOME=/tmp/evil`, `TMPDIR=/tmp/evil-world-writable`, each containing a fake `gpgv`, a fake `sudo`, and a `.gnupg` directory; assert no `/tmp/evil/*` binary is executed (verified by the fake binaries creating a marker) and that verification results come from the plan, not from a re-run. *Fails when* any marker appears or any `TMPDIR`-derived path is used by the root run.
- **S13 — Environment not inherited.** Start the write with a `sudo -E`-style environment (`APT_CONFIG`, `LD_PRELOAD`, `TMPDIR`): all ignored, and the write performs the same file operations it would with a clean environment. *Fails when* any of them changes which targets are written or which bytes are used.
- **S14 — the write makes no network request and spawns no external process.** With `--network none` once the validation layer is reached, and a `strace`-free check: complete a write and assert it opens no socket and spawns nothing. Then re-run with `/usr/bin/gpgv` removed after verification has already happened (test hook) and assert the write still succeeds. *Fails when* removing `gpgv` changes the write's outcome — which would prove the write re-verifies — or the write opens a socket or a child process.
- **S15 — The D6f P1 regressions still gate the write, not only the display.** `noble-updates-InRelease.prefixed` (forged `Date:` before the armour): a read-only run ranks it under the current tolerance, and a write run refuses to select it. Plus a write whose recomputed disk digest disagrees with the bytes it validated is refused before the first write. *Fails when* either path accepts it. A forged proof is not a test case: the value cannot be constructed without the verification pass (3.10), and `the_write_proof_is_minted_only_in_the_verifier` (`src/verify.rs:624`) is the unit test that keeps it that way.
- **S16 — Disposable-container rule.** The harness gained the control in D9c, and it is stricter than the rule asked: there is no `/etc/apt` override in any build. A write case uses the disposable container's own `/etc/apt`, and the harness that reaches it is compiled out of every other build — `#[cfg(apt_scout_write_harness)]` gates the module (`src/main.rs:8–9`) and its dispatch before argument parsing (`src/main.rs:610`), so a default or release build contains no harness code at all and `__write-harness` is an unknown option there. The runtime half is the guard: `require_container` refuses to plan anything unless `/.dockerenv` or `/run/.containerenv` exists (`src/harness.rs:303`), and every write case starts through `wrun`, a container with `--network none`, one read-only binary mount and no other mount (`scripts/docker-test.sh:106`) — never a bind mount of the host's `/etc/apt`. Because the container root is the fixture and the binary carries no path, a write case cannot be pointed at a host path at all. *Fails when* a write case can be pointed at a host path, or a release binary accepts anything but the default `/etc/apt`.
- **S17 — Pre-existing Pop!_OS security file.** On a Pop!_OS fixture, `/etc/apt/sources.list.d/system-security.sources` already exists (both as a regular file and as a symlink): `EEXIST` aborts the whole apply, every target digest is identical afterwards, the pre-existing file is byte-identical with its mode and owner unchanged, and no half-written backup directory is left behind. *Fails when* the file is overwritten, followed as a symlink, or any other target changed.

## 8. The three gaps the first review left open, and their rulings

The first independent security review left three gaps open. All three are ruled by the user (2026-11-12, relayed by the parent orchestrator). Each entry states the decision, why it is fail-closed, the abuse path it closes, and the tests that check it. No gap is left open, so this section no longer blocks D9; the independent security review's PASS verdict is what remains for D6e.

**G1 — the restore source, and who may read it.** Source: audit P1-3 and P1-4. Ruled: the restore run reads `/var/backups/apt-scout/<id>/MANIFEST` by a path it builds itself, aborts before parsing a byte unless that path is a regular file owned by root with mode 0600 and not a symlink, and only then re-derives the target set and every per-target digest from the manifest, refusing the restore when a record's digest, mode or owner disagrees with the backup copy it names (section 5). The backup directory is 0700 root-owned and the manifest 0600, so only a run that holds root can read them, and both the read and the write of a restore are root. The manifest is the source of truth for what is written, never a list the run already chose, so a stale or partial manifest cannot apply a subset of the backup. Carried by 5 and 7.7; `SPEC.md` Apply and CLI; S4, S10.

**G2 — removed 2026-11-12.** Plan integrity "content, not producer" (audit P1-6) existed because a plan crossed a process boundary and an unprivileged producer could hand root shape-valid bytes. No plan crosses a boundary now, so there is no producer to distrust: the digests that remain bind the bytes to the disk state the run validated, not one process to another. Removed with 7.2 and 7.3. Tests: none of its own; S6 and S15 carry what is left.

**G3 — one binary, out of scope for v1.** Source: review P2-4. Ruled, in the user's own framing: the program is not complicated, so it **is one binary**. The second-artifact trigger and its line-count threshold are removed outright — not left reopenable by a human, not restated as a signal a reviewer may raise. 4.6 now states that a split of the root run into a second artifact is out of scope for v1, and that any future split would be a new product decision taken by the user with the threat model 4.4 requires, never something a size measurement or a review finding can trigger. `SPEC.md` Privilege boundary and threat model carries the same statement for behavior. Abuse path closed: an agent reading the size of the write path as authorization to ship a second root artifact that no audit covers. No test of its own; 4.4's C-spawned-by-root entry stays rejected.
