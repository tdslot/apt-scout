# apt-scout SPEC

Standalone Rust CLI.
Picks the fastest, fresh, nearby Ubuntu archive mirror and rewrites apt sources.
Equivalent of `nala fetch` without installing nala.
No Python or other runtime.

This file is the map: the requirement text lives in `docs/spec/`, one file per area.

## How to read

- `docs/spec/` is normative: what apt-scout MUST, SHOULD and MAY do, one requirement per bullet.
  Code, tests and reviews are held to it.
- `docs/decisions/` holds the decisions behind that text and the evidence that settled them.
  A decision is not a requirement; where the two disagree, the requirement wins.
- `docs/threat-model.md` is the privilege-boundary record: what may reach the one process that
  writes as root.
- `GLOSSARY.md` defines the vocabulary.
  A requirement uses those terms and no others.
- `ROADMAP.md` is the execution ledger: task order, states, merged pull requests and verification
  evidence.
  The `State` column below summarises it, and where the two disagree `ROADMAP.md` wins.

## Scope (v1)

- Ubuntu and derivatives, detected from `/etc/os-release`; codename and architecture rules are in
  `docs/spec/platform.md`.
- Debian: out of scope (different mirror list).
  Unsupported distro -> exit with clear error.
- Only official Ubuntu archive URIs are rewritten (and `apt.pop-os.org/ubuntu` on Pop!_OS).
  `security.ubuntu.com`, PPAs, third-party repos are never touched.

| `APPLY-1` | `docs/spec/apply.md` | One code path writes, and it is internal. Discovery, verification, rewrite planning and confirmation produce a plan; the plan is validated against the closed target enumeration and the current on-disk state; only then does the first byte change. The plan is never a file, never a message on stdin, and never a flag: the user does not type a step of it, and it does not cross a process boundary. It names files through a fixed enumeration and carries the selected mirror, the verification result that authorizes writing it, the exact bytes, mode, and owner of every file it was computed from, and the exact bytes to write. It carries no freshness baseline of its own: the caller establishes one from the canonical reference when that reference has a verified `-updates` `Date` read inside the signed region, otherwise from the newest candidate in this run that carries one, after the clock-skew sanity guard of `pipeline.md` step 8, and the writer holds the selected mirror's proof against it before the first byte, refusing outright when no verified baseline was supplied, because a writer that may not fetch cannot establish one. The write aborts, before its first byte, on any missing field, any mismatch with the file on disk, any digest it cannot recompute to the same value, any target that is not a regular file after resolution, and any plan it did not fully validate. The plan binds to the disk by comparing those bytes, not by a hash; every digest the manifest records is SHA-256 over the exact bytes it describes. The write performs no network request of its own, invokes no shell, resolves no command through `PATH`, and reads no environment variable. Never write without root. The confirmation prompt is a safety rail, not a security control: the guarantee is the validation, and `--yes` removes only the prompt. A `--restore` plan is authorized by the backup it was re-derived from instead of by a verified mirror: it carries no selected mirror and no baseline, the baseline rule above is a mirror's rule, and every other requirement in this bullet applies to it unchanged. Only a `--restore` plan may remove a file: a removal is the one effect a restore can prove from the manifest it re-derived the plan from, so a plan that would remove anything while authorized by a mirror is refused before its first byte. A replacement is legitimate under either authority; a creation is legitimate only under a mirror plan, because a restore plan carries no platform and a creation without one is refused. | implemented |
| `RESTORE-1` | `docs/spec/apply.md` | `--restore` copies the newest backup back, in one root run: it reads `/var/backups/apt-scout/<backup id>/MANIFEST` itself and aborts before parsing a byte unless that path is a regular file, owned by root, mode 0600, and not a symlink. It then re-derives the target set and every per-target digest from the manifest itself and validates them: every entry matched to the closed target enumeration, every path under `/etc/apt/`, a regular file after resolution, and every recorded digest, mode and owner matching the backup copy it names, refusing the whole restore on the first disagreement; a file the run created has no backup copy, so its record carries the digest, mode and owner the run created it with, and the restore refuses to remove it unless the file on disk still matches. The manifest is the source of truth for what is written, not a list of files the run already chose, so a stale or partial manifest cannot apply a subset of the backup. `--restore` does not depend on the rewrite logic, and it reaches the writer through the same validation as an apply. It is executed by that same writer, through the one entry point the writer has: the restore engine re-derives the plan and hands it over with no baseline, so a restore adds no second write path and no write code of its own. The newest backup is the greatest id under `/var/backups/apt-scout/`, because the ids are zero-padded UTC timestamps and their string order is their age; it is the only backup a run considers, so a restore whose newest manifest or copy is refused fails as a whole and never falls back to an older backup, and a backup root that holds no id, or an id whose directory is not a plain directory, is a failure that writes nothing and exits 1. A restore is itself a write and backs up every file it replaces or removes under its own id, exactly as an apply does, so after one restore the newest backup is that restore's; the file it removed is one of them, recorded there as a file to put back with the bytes it held and with a copy beside it, so what refuses a second restore from that backup is the disk rather than the manifest — the record says replace and the target is gone — which is the record-versus-disk rule above rather than a guess. | implemented |

| `APPLY-3` | `docs/spec/apply.md` | Rewrite per URI token, not per file or line. Rewrite a URI when its host is `archive.ubuntu.com`, `*.archive.ubuntu.com`, or a host and path the Launchpad mirror list names in any country, not only the run's own country, so a mirror this tool wrote stays rewritable after the operator changes country: otherwise a choice the tool made can be undone only by hand, which the run that made it must not leave behind. Membership answers recognizability, not trust: it makes an existing URI eligible for replacement and nothing else — the replacement is still the selected candidate, validated and with its `-updates` `InRelease` verified per probe, and the list source is trusted no further than it already was. Eligibility is by the listed URL's host and path, not by the host alone: an on-disk URI token is eligible only when its host matches a listed mirror's host and its path begins with that listed entry's path, compared by whole segments, so a listed `/ubuntu` admits `/ubuntu/` and `/ubuntu/dists/...` but not `/ubuntufoo`. A mirror host usually carries several trees and only the Ubuntu tree is what this tool may replace: `deb http://ftp.uni-stuttgart.de/debian trixie main` is left alone even when that host is listed as an Ubuntu mirror at `/pub/linux/debian/ubuntu/`. A listed entry whose path is `/` admits every path on that host, because the list names no narrower tree there and the tool cannot tell the trees apart; that is acknowledged rather than hidden, and it is why the canonical archive and its `*.archive.ubuntu.com` names stay recognized at any path. A dot segment is never eligible and never enters the set: a token whose path carries `.`, `..`, or the `%2e` spelling of either is left unchanged with a reason naming the segment, and a listed entry whose path carries one is dropped and reported, so neither the any-path rule above nor a listed prefix can admit a path that traversal would resolve elsewhere. The test is lexical and reads exactly one spelling layer: a segment counts as `.` or `..` when `%2e`, in either case, is taken as a dot, no other escape is decoded, and no segment is resolved, so `%252e` is a literal segment name and `...` is an ordinary segment. The port is not part of the comparison, as before. `--https-only` does not narrow what is recognizable: a mirror written over `http` stays recognizable in a later `--https-only` run. Every entry of every list source passes the same candidate URL validation before it may enter the set, the Launchpad page and the `mirrors.ubuntu.com` fallback alike, and an entry that fails is reported and left out, never silently trusted. Launchpad is the only list that names every country; `mirrors.ubuntu.com` is read one country at a time (`<CC>.txt`) and its `mirrors.txt` names only the canonical archive, so outside Launchpad the eligible hosts and paths are the ones in the file the run did load and an entry outside it is reported as skipped rather than rewritten. The set therefore fails closed in the only direction open to it, shrinking and never widening, and when no URI is eligible the run stops under the no-eligible-URI rule and touches nothing. A path prefix is a recognition rule and its cost is stated here rather than discovered later: when a host is listed at a path other than the one an on-disk URI carries — a listing that changed its layout, or an entry since delisted — that URI is reported as skipped with its reason and left unchanged, not forced through. Naming those hosts is the point: before this rule a PPA was safe only because no list happened to name a PPA host, which is not a control. A line or stanza whose suites include a `-security` suite is never rewritten to a probed mirror, even when its host is `archive.ubuntu.com`, because `-security` freshness is not checked; report each skipped entry and why. The only exception is the Pop!_OS split above, which keeps `-security` on the original mirror. On Ubuntu 24.04 and later security already lives in its own stanza (`security.ubuntu.com`), so no split is needed. | implemented |

| `NFR-10` | `docs/spec/non-functional.md` | Freshness trust boundary: ranking may display and use an `InRelease` `Date` even when signature verification is `invalid` or `unavailable`; this can mis-rank a mirror but cannot authorize package installation. Every `-updates` `InRelease` used by probing is verified with `/usr/bin/gpgv --keyring /usr/share/keyrings/ubuntu-archive-keyring.gpg`, using no shell, no `PATH` lookup, a cleared environment, a private 0700 temporary directory that is also `gpgv`'s `--homedir` (so no user GnuPG configuration or default home can influence the result), a 10-second process timeout, and a 1 MiB cap on captured status output. The download cap is the verifier's own 512 KiB cap, so an oversized file is rejected at download instead of being reported as an unverifiable but rankable mirror. The informational `-security` pocket is read as a ranged head of 4 KiB and is never verified, because nothing consumes its signature. Missing/invalid `gpgv` or keyring, unsigned/changed/unknown-key data, oversize data, and execution errors are shown explicitly and are never `Verified`. Only a `Date` from inside the cleartext-signed region (`pipeline.md` step 8) is ever trusted: bytes before `-----BEGIN PGP SIGNED MESSAGE-----` or after `-----BEGIN PGP SIGNATURE-----` are outside what `gpgv` signs, so a `Date` read there is shown and ranked, is never a verified date and never authorizes a write. Ranking may use a `Date` whose status is `invalid` or `unavailable`, but only a `Verified` `Date` parsed inside the signed region is usable by a write. Before a write may use a ranked mirror, the selected mirror's `-updates` `InRelease` and the write baseline must both be `Verified`. Ranking has a separate baseline that ignores verification and may fall back to the newest candidate `Date`, verified or not. The write baseline may not ignore verification: it is the canonical reference when that reference's own `verified_updates` field is `Some`, and otherwise the newest candidate whose own `verified_updates` field is `Some`; when neither the canonical reference nor any candidate yields one, a write fails closed. Trusted freshness dates are represented by a value that only a `Verified` status can construct (`VerifiedDate`), and the probe result, the reference and the ranked entry each expose it, so a write path takes that value and never a bare `Date`. ## Privilege boundary and threat model

- Security goal: untrusted inputs must not let an attacker execute code as root or write outside
  the explicitly allowed apt paths through apt-scout.
- Treat CLI arguments/environment, apt source contents, network responses, mirror URLs, backup
  manifests, file metadata/races, and terminal input as untrusted.
- One process writes, and the accepted cost is stated here rather than hidden.
  In a root run the networked discovery and the parsing of untrusted responses — geolocation, mirror
  lists, `InRelease` bodies — happen in the same root process that later writes, because that is the
  workflow the user chose when running `sudo apt-scout`.
  What defends the user is the order of operations: nothing is written until the selected mirror's
  `InRelease` verifies and the internal plan validates against the on-disk state.
  A two-process split that keeps the network phase out of root is future work and is not a supported
  flag in v1.
- The write path must use fixed executables/paths and a minimal controlled environment; it must
  not invoke a shell and must not resolve a command through `PATH`, and after verification it spawns
  no external process.
  Validate file type, ownership/mode policy, path containment, and symlink/TOCTOU behavior at the
  point of use; fail closed on any mismatch.
- The program never re-execs itself privileged, never invokes `sudo`, and is never installed setuid.
  Privilege is obtained only by the user running the program as root.
  A root run is the same binary with the same code; the only thing that changes is that it may write.
  Security review reduces risk but is not a guarantee of absolute immunity.
- What a write is bound to: the bytes it writes are the bytes its own validation passed, over a
  disk state that still matches the digests it computed.
  Every target's new content carries a digest the writer recomputes, and a mismatch is refused.
  The confirmation prompt is a safety rail, not a security control: the guarantee is the validation,
  and `--yes` removes only the prompt.
- The writer is one code path in one binary, shared by the default run, the TUI confirm, and
  `--restore`.
  A separate privileged artifact is out of scope for v1, as is a two-process split; either would be
  a new product decision, not something a size measurement or a code review finding can trigger.
- Before D9 or any write implementation, D6c, D6e, and D6f must be complete.
  Every write PR needs a security-focused exact-diff review and disposable Ubuntu-container tests
  for path traversal, malformed manifests, symlinks/races, backup failures without partial writes,
  rollback, and rejection of paths outside `/etc/apt`.
  Never run write tests on the developer host.

## Resilience

Third-party services change formats, add limits or become paid.
The program must keep working when they do.

- Geolocation and AS lookups are optional.
  If country detection fails, the program asks for `--country`, or runs with `--any`; it never
  silently guesses a worldwide list, and the one widening `docs/spec/pipeline.md` step 4 describes is announced, refused
  when the loaded list names one country, and never a substitute for a detected country.
  If AS lookup fails, ranking proceeds without AS preference.
  Failures include source and reason.
- Core data comes from sources the project depends on anyway: the Ubuntu archive (`InRelease`),
  Launchpad mirror list, DNS.
  No account, key or paid tier is needed anywhere.
- Parsers reject unexpected shapes instead of guessing, and report which field was missing.
- Weekly contract check (`.github/workflows/source-contract.yml` runs
  `.github/scripts/check-sources.sh`; the script can be run locally; not a required check): fetch
  each live source once, check that the fields the parser needs are still present, and open an issue
  only after two consecutive failures (runner IPs can be rate limited by individual services).
  Scheduled workflows on public repos are disabled after 60 days without repository activity; the
  check is advisory.

## Out of scope (v1)

Debian, Fedora/other package managers, running `apt update`, scheduling, GUI, PPA mirrors.
