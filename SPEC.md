# apt-scout SPEC

Standalone Rust CLI. Picks the fastest, fresh, nearby Ubuntu archive mirror and rewrites apt sources. Equivalent of `nala fetch` without installing nala. No Python or other runtime.

## Scope (v1)

- Ubuntu and derivatives, detected from `/etc/os-release` `ID` / `ID_LIKE`. The codename is `UBUNTU_CODENAME` when present, otherwise `VERSION_CODENAME`: Linux Mint reports `VERSION_CODENAME=wilma` but apt uses Ubuntu's `noble`.
- Pop!_OS (`ID=pop`, `ID_LIKE="ubuntu debian"`, `UBUNTU_CODENAME` equals the Ubuntu base, for example `jammy`): supported. Verified from the real `pop-default-settings` package (`/etc/pop-os/os-release`, `postinst`): the active source is the deb822 file `/etc/apt/sources.list.d/system.sources` with `URIs: http://apt.pop-os.org/ubuntu`, `Suites: <codename> <codename>-security <codename>-updates <codename>-backports`, and `X-Repolib-Default-Mirror: http://apt.pop-os.org/ubuntu`. `apt.pop-os.org/ubuntu` is a true Ubuntu mirror (`Origin: Ubuntu`, same `InRelease` Date as `archive.ubuntu.com`). Rewrite rules for Pop!_OS: rewrite only the `URIs` of `system.sources`; leave `X-Repolib-Default-Mirror` unchanged (it is the vendor default kept for restore, as `apt-manage` treats it); never touch System76's own repositories (`apt.pop-os.org/release`, `apt.pop-os.org/proprietary`, `pop-os-apps.sources`). `apt.pop-os.org/ubuntu` is treated as an official archive URI for Pop!_OS only. Because Pop!_OS keeps `-security` in the same stanza as the other suites, the rewrite moves it: `system.sources` keeps the non-security suites with the new mirror, and a new file `/etc/apt/sources.list.d/system-security.sources` holds a stanza for the `-security` suite on the original mirror (this is the one case where apt-scout creates a file in `/etc/apt/sources.list.d`; it is recorded in the backup manifest and removed by `--restore`). The new stanza gets a different `X-Repolib-Name` (`Pop_OS Security`) and copies `Types`, `Components`, `Enabled` and `Signed-By` from the original. Verified in a container with the real repolib 2.2.2 package: two stanzas with the same `X-Repolib-Name` in one file are merged on `load()`+`save()` (the first stanza gains the `-security` suite), so splitting inside one file is unsafe; separate files with different names load and save unchanged. The pure D8 transformation returns both the rewritten `system.sources` content and the planned new `system-security.sources` content without filesystem IO; D9 owns file creation, backup and atomic write. The diff shows the split before anything is written. `repolib`/`apt-manage` may add `X-Repolib-ID: system` on save; that is harmless. Tools such as `pop-upgrade` or `apt-manage` can later reset the URIs to the vendor default; the rewrite is then simply undone, which is acceptable. Check whether the `pop-default-settings` `postinst` overwrites `system.sources` on package upgrade (it only creates the file when missing, so an upgrade does not overwrite it).
- Debian: out of scope (different mirror list). Unsupported distro -> exit with clear error.
- Only official Ubuntu archive URIs are rewritten (and `apt.pop-os.org/ubuntu` on Pop!_OS). `security.ubuntu.com`, PPAs, third-party repos are never touched.
- Architectures `amd64` and `i386` only (from `dpkg --print-architecture`). Other architectures (arm64, ...) use `ports.ubuntu.com`, which has no mirror choice: print an explanation and make no changes.

## CLI

Single command, no subcommands: `apt-scout [flags]`

No flag is required. The uid decides whether the run writes: it discovers, ranks and recommends, and a non-root run prints the one line that repeats the run under `sudo` and exits 3, while the same command under `sudo` writes the best mirror. Every flag below is an override, never a step in the workflow.

| Flag | Meaning |
| --- | --- |
| `--country <CC>` | ISO 3166 alpha-2 override. Always wins over detection. |
| `--refresh` | Ignore the geo, mirror list and AS caches for this run (and rewrite them). |
| `--no-geo` | No geolocation lookups at all. Requires `--country`; AS preference is skipped. Offline-friendly for the server lookup. |
| `--top <N>` | Show N best mirrors (default 5). |
| `--https-only` | Only consider https mirrors. |
| `--tui` | Interactive mode: ranked table, selection, detail panel, confirmation. Opt-in; the default run is not interactive. |
| `--list` | Table and planned change only; never writes, whatever the uid. |
| `--yes` | Skip the one confirmation before a write in a root run. |
| `--restore` | Restore the newest backup instead of applying a mirror. Root is needed for the read of the backup and for the write. |

Command, uid, and whether apt sources change:

| Command | uid | Writes apt sources |
| --- | --- | --- |
| `apt-scout` | non-root | No: discovery, ranking, the recommendation with its reason, the one line `sudo apt-scout`, exit 3. |
| `sudo apt-scout` | root | Yes: the same discovery and recommendation, one confirmation (`--yes` skips it), the write. |
| `apt-scout --list` | any | No: the ranked table and the change a write would make, exit 0. |
| `apt-scout --tui` | non-root | No: the interactive selection, then the one line `sudo apt-scout --tui`, exit 3. |
| `sudo apt-scout --tui` | root | Yes, on the confirmation dialog: the selection the user arranged is written. |
| `apt-scout --restore` | non-root | No: the one line `sudo apt-scout --restore`, exit 3. |
| `sudo apt-scout --restore` | root | Yes: the newest backup, after one confirmation (`--yes` skips it). |

Behavior by mode:
- Every run prints the ranked table, then the recommendation and its reason: host, country, AS match, speed, lag and signature status. Rejected mirrors are listed with the reason they were rejected.
- A write confirms once: the files it will change, the old URI and the new one, the alternatives, and the backup path it will create. `--yes` skips that prompt. The prompt is a safety rail, not a security control: the guarantee is the validation described in Apply, and no answer to the prompt can bypass it.
- A non-root run without `--list` prints the table, the recommendation and one line, then exits 3: `sudo apt-scout` with the flags of that run repeated. It opens no apt file for writing.
- `--tui` is opt-in and is never chosen for the user. The default run is non-interactive, so no flag turns the TUI off.
- `--restore` replaces the source of the rewrite: the newest backup instead of the mirror pipeline. Root is needed for that read as well as for the write, so the non-root run prints only `sudo apt-scout --restore` and exits 3 before it opens the backup.
- No step of the write is a mode the user types. Building the plan, validating it against the closed target enumeration and the current on-disk digests, verifying the mirror's `InRelease`, and writing are one code path inside the program (see Apply); the plan never crosses a process boundary and is never a file.

## Pipeline

1. **Detect distro** from `/etc/os-release`. Read the codename: `UBUNTU_CODENAME` when present, otherwise `VERSION_CODENAME` (Linux Mint reports `VERSION_CODENAME=wilma`, but apt uses `noble`).
2. **Detect location** of the server (country, then AS), skipped with `--no-geo`. Every source is optional: if all fail, the program asks for `--country`; it does not guess a worldwide list. The mirror-list sources themselves are Launchpad for the selected country, then the `mirrors.ubuntu.com` country list. Sources are tried in order and the first valid answer wins; web sources use HTTPS except Canonical's endpoint noted below; AS comes from DNS.
   1. Country: Canonical `http://geoip.ubuntu.com/lookup` (XML, field `CountryCode`; the same endpoint the Ubuntu installer uses; plain HTTP, so treat the answer as untrusted and validate it). Fallbacks: `https://ifconfig.co/json` (`country_iso`, operator asks for at most 1 automated request per minute), `https://ipinfo.io/json` (`country`), `https://www.cloudflare.com/cdn-cgi/trace` (`loc=<CC>`).
   2. AS of the server: Team Cymru DNS, TXT query for `<reversed-ip>.origin.asn.cymru.com` (IPv6: `<nibble-reversed-ip>.origin6.asn.cymru.com`; answer `AS | prefix | CC | registry | date`; the `CC` is the registry country, not a location, so it is never used as the server country). No web API and no HTTP: plain DNS through the system resolver. Fallback in the current implementation: the already-fetched `ifconfig.co` or `ipinfo.io` `asn`/`org` fields. RIPEstat is planned, not yet implemented.
   - To query Cymru the server's public IP is needed: take it from whichever HTTP source answered (geoip, ifconfig.co, ipinfo, Cloudflare `ip=`). If none answered, AS is unknown.
   - No retries: any failure (timeout, non-200 including 429, malformed body, DNS error) falls through to the next source. HTTP requests use a 10 s whole-request timeout, including redirects. Geolocation responses are capped at 256 KiB; the mirror-list page has a 2 MiB cap. The maximum chain duration depends on which sources fail and whether later AS queries are needed; AS DNS lookup has a 12 s total per-query budget and mirror-AS ranking has a 20 s overall budget. Print which sources failed and why.
   - Validation: country is uppercased and must match `^[A-Z]{2}$`; `XX` (unknown), `T1` (Tor) and `Unknown` are treated as unknown. The same rule applies to `--country`.
   - AS normalization: every source's value becomes canonical `AS<number>`. Take the first whitespace-delimited token of `org`/`as`, prefix bare integers with `AS`, validate `^AS[0-9]{1,10}$`, compare numerically. Empty or malformed means unknown. For a prefix with several origin ASNs the first listed is used; this is approximate.
   - `--country` overrides the country only; AS is still looked up unless `--no-geo`.
   - Cache is planned, not yet implemented.
   - Privacy: live geolocation web services learn the server's public IP; system DNS and Team Cymru receive the IP inside a DNS query. Candidate mirror host IPs are sent to DNS and Team Cymru for AS lookup. `--no-geo` skips all these lookups and requires `--country`.
   - `--country` replaces only the country answer; the chain still runs to learn the public IP for the AS lookup unless `--no-geo`.
**Preflight before any network access:** validate CLI country values against the supported country table and validate the local architecture. Invalid country/unsupported architecture must fail before geolocation or any HTTP/DNS request. Resolve this before invoking geo or mirror-list sources.

3. **Load mirror list**, first success wins, source shown in output:
   1. Launchpad `https://launchpad.net/ubuntu/+archivemirrors` (HTML, ~316 KB, ~560 mirrors in ~80 countries). Measured structure: a `<tr class="head">` row with `<th colspan="2">Country</th>` starts each country; each mirror row has a `/ubuntu/+mirror/<id>` link, one `<a href>` per protocol (`https`, `http`, `ftp`, `rsync`; only `http(s)` are used), a speed (`10 Gbps`), and a status `<span class="distromirrorstatus{UP|UNKNOWN|...}">`. Launchpad's own status (`UP` = up to date) is used as a hint, never as proof of freshness. Measured: 82 country sections, 562 mirror rows, only `UP` and `UNKNOWN` statuses seen, speeds from `128 Kbps` to `100 Gbps`, and 2 rows with only `ftp`/`rsync` links (skip them, they cannot be probed over HTTP). The parser must tolerate missing protocols and unknown statuses, and is tested against a saved fixture of this page.
   2. `http://mirrors.ubuntu.com/<CC>.txt` (plain text, one URL per line, already ordered by geographic proximity, ~6 URLs, no speed or status). Used when Launchpad fails or returns no mirror for the country.
   3. Disk cache `~/.cache/apt-scout/mirrors.json` (valid 24 h; stale cache used only if all else fails, with a warning)
   4. Snapshot compiled into the binary (dated; warn when older than 90 days)

   Each network source: one 10 s time budget per call covering redirects (no retries in v1: a failure falls through to the next source), response validated (non-empty, at least one well-formed `http(s)://` URL; for Launchpad, at least one country section). Invalid response counts as failure.
4. **Filter**: mirrors in the detected country only. v1 does not top up from nearby regions or worldwide; if a country has no usable mirror, the run says so and the user picks another with `--country`. Candidates are deduplicated (ignoring a trailing slash and case), capped at 30, and `--https-only` drops http. An unknown country code (not one of Launchpad's 82 countries) is a usage error (exit 2) before any network request; it does not fall back to `mirrors.ubuntu.com/<CC>.txt`.
5. **Resolve AS** of candidates (skipped with `--no-geo`; informational, never a reason to fail the run): resolve each hostname to an IP, then Team Cymru DNS TXT per IP (parallel, cap 8 at a time), normalized as in step 2. No per-IP fallback is implemented yet; failures leave AS unknown. Cymru client: hand-rolled raw UDP query (about 80 lines; std has no TXT API and an async resolver crate contradicts the no-async rule). Read nameservers from `/etc/resolv.conf` (up to 3; the systemd-resolved stub `127.0.0.53` and Docker's `127.0.0.11` handle TXT), use an absolute name with a trailing dot (no search-domain expansion), connect the UDP socket, use a transaction ID, validate the reply ID and `QR` bit, cap compression-pointer traversal, treat NXDOMAIN as AS unknown, and treat the `TC` (truncated) bit as failure (no TCP fallback). Missing `resolv.conf` means AS unknown. No HTTP batch API and no rate-limited free tier is required. AS caching is planned, not implemented. CDN-backed mirrors can resolve to different AS per query; AS is approximate. Current implementation resolves the first address returned by the system resolver; IPv6-specific candidate selection is not implemented yet.
6. **Fetch reference** once, before probing: from `http://archive.ubuntu.com/ubuntu/dists/<codename>-updates/InRelease` and `<codename>-security/InRelease` get the `Date:` of each pocket. The `<codename>-updates` reference is downloaded in full under the 512 KiB download/verification cap and its OpenPGP signature is verified, and both its `Date` and its signature status are kept, because it is the freshness baseline a write may trust. The `<codename>-security` reference is a ranged 4 KiB head and is never verified, because nothing may consume its signature. This is the freshness baseline. The `<codename>` release pocket is not compared: its `Date` is the release date (for example `noble` shows April 2024) and never changes, so it says nothing about freshness.
7. **Probe** each candidate in parallel (`std::thread`): fetch `<mirror>/dists/<codename>-updates/InRelease` in full under the 512 KiB download/verification cap so its OpenPGP signature can be checked, and fetch only the head (`Range: bytes=0-4095`) of `<mirror>/dists/<codename>-security/InRelease` for the informational `Date`. Measure time to first byte (DNS, TCP, TLS and one round trip) on the `-updates` request, never the body download time. Measure throughput on a larger sample (`Range: bytes=0-1048575` of `main/binary-<arch>/Packages.xz`), because the ~130 KB `InRelease` is too small and too variable to measure throughput. Redirects: follow at most 3, re-validate the final host and scheme; report mirrors that redirect to another host.
8. **Reject** unreachable mirrors, non-200 responses, and stale mirrors. `<codename>-updates` decides: a mirror is stale if its `Date` is older than the reference by more than `MAX_LAG` (24 hours). `<codename>-security` lag is shown for information only, because `security.ubuntu.com` is left untouched. A missing `-updates` pocket or unparsable `Date` rejects. A `Date:` is trusted only when it is inside the cleartext-signed region: nothing but whitespace-only lines may precede `-----BEGIN PGP SIGNED MESSAGE-----`, which must itself start its line (`gpgv` refuses a space-prefixed armour header), the armour headers that follow it are skipped up to the first blank line, and the search stops at `-----BEGIN PGP SIGNATURE-----`. A body with any other content before the armour header, or with its only `Date:` after the signature header, still has a good signature: `gpgv` accepts such a prefix, so its signature status is `verified` and is displayed as such, and naming it `invalid` would change what the status means. What such a body cannot supply is a trusted `Date`: a `Date` read outside the region is never a verified date, never a write baseline and never authorizes a write, because a write takes only a date parsed inside the region, so the parser, not the verifier, separates a signed `Date` from a displayed one. Read-only ranking keeps its tolerance: a `Date` read outside the signed region is still used for lag, ranking and the table, so a mirror that serves one is ranked, not rejected. An `InRelease` larger than the 512 KiB download/verification cap is rejected at download, because the verifier would refuse it anyway. That oversized rejection applies in read-only mode too: the promise that read-only ranking still works covers a missing or unusable `gpgv`, not a mirror that sends more than the cap. `Date` is the signing time, not the sync time. If the reference host is unreachable (network error, 5xx), use the newest `Date` among candidates as baseline and print a warning; a `Date` more than `MAX_LAG` ahead of the median is treated as bogus and ignored, so one wrong clock cannot make every other mirror stale. Only the `<codename>-updates` reference decides whether the release left the archive; an unreadable `-security` reference is ignored (it is informational). If the reference answers 404 for the codename, the release is no longer on `archive.ubuntu.com` (it moved to `old-releases.ubuntu.com`, which has no mirrors): exit 4 with a message that names the codename and explains this; never use the newest-candidate baseline in that case. Measured on 2026-11-11 (`noble-updates`): of 10 Lithuanian and Norwegian mirrors, 6 matched the reference exactly and 4 were identical to each other but one signing generation behind (about 6 hours), so a 1-hour limit would reject 40% of good mirrors. Freshness also guards against replay of old indexes; apt still verifies signatures.
9. **Rank**: compare `-updates` `Date` exactly (no tolerance); lag is the reference `Date` minus the mirror `Date`, clamped to 0 because the reference is fetched first and a mirror may be newer. Primary key: lag ascending (mirrors with equal `Date` form one group). Within a group: throughput descending, then latency ascending; a mirror in the same AS as the server wins when its throughput is within 20% of the group's fastest mirror (band measured against that top speed, so it is not chained). A lagging but not stale mirror stays selectable and shows a warning. Accepted trade-off: a slow mirror with the exact reference `Date` ranks above a much faster one that is one signing generation (about 6 hours) behind. CLI output must show the actual mirror AS (or `unknown`) and same-AS status (`same`, `different`, or `unknown`) so users can understand and audit the AS tie-break; do not imply AS preference when lookup failed.
10. **Plan and write**: build the plan described in Apply, validate it against the closed target enumeration and the current on-disk digests, and only then write. A run that may not write stops after the recommendation. No step of this is user-visible or separately invocable.

## TUI

Library: `ratatui` + `crossterm` (no async). Opens only with `--tui`, after probing finishes (a progress view is shown while probing).

- Layout: ranked mirror table (left/top), a detail panel for the highlighted mirror, and a footer with the active keys.
- Table columns: checkbox, rank, host, country, scheme, latency, throughput, lag (updates), AS match, signature, `Recommended` badge.
- Detail panel: full URL, country, AS number and name, resolved IP, scheme, time to first byte, throughput, `Date` and lag for `-updates` (decides) and `-security` (informational), AS match, signature status of the `-updates` `InRelease`, mirror list source, status or rejection reason.
- Recommendation: the best-ranked mirror is pre-checked and carries the `Recommended` badge. Rejected mirrors are shown dimmed, with the reason, and cannot be checked.
- Selection: multiple checkboxes. The first checked mirror in rank order is the primary (active URI); other checked mirrors are written as commented `alternative` lines (see Apply).
- Keys (arrows are primary; `j/k` not required):
  - `Up`/`Down`: move in the focused section. `Left`/`Right`: switch tab/page within a section (e.g. the `-updates` and `-security` detail tabs) or collapse/expand details.
  - `Tab`/`Shift+Tab`: cycle focus between sections (mirror table, detail panel, buttons).
  - `Space`: toggle checkbox on the highlighted mirror.
  - `Enter`: confirm the current step or dialog (accept, yes).
  - `Esc`: cancel the current action or close a dialog; on the main screen, quit without changes (asks to confirm if the selection was changed).
  - `Insert` (implemented in the last milestone): add an entry: opens an input dialog for a custom mirror URL (validated, then probed like any candidate and added to the table).
  - `Delete`/`Del` (last milestone): remove the highlighted entry from the list (asks to confirm; only affects the current run, never apt files).
  - `r`: re-probe. `?`: help.
- Zero-effort flow: defaults must be right, so pressing `Enter` through the flow saves the best fresh mirror among the existing candidates. Keep the step count minimal, but never hide information the user needs. Base path (3 steps):
  1. Mirror table with the `Recommended` mirror pre-checked and a one-line summary of what will change; `Enter` continues.
  2. Confirmation dialog `Apply changes? [Yes]`: lists the files to change, old URI -> new URI, alternatives, and the backup path; `Yes` focused. As root, `Enter` validates the plan and writes it, so the dialog is the confirmation and `--yes` is not needed. As a non-root uid, `Enter` prints the one line `sudo apt-scout --tui` and exits 3; the TUI writes nothing.
  3. Result screen: as root, `applied <mirror> to <files>`, the backup path the write created, how to undo (`--restore`), and the suggested `apt update`; as a non-root uid, `nothing written, run sudo apt-scout --tui`, the files the write would change and the backup path it would create. `Enter` exits.
- Extra steps appear only when the user must be informed or decide: selection has warnings (e.g. only http, lag near `MAX_LAG`, different country), a custom mirror failed its probe, no fresh mirror found, the write failed (show the reason and the state of the backup, which is untouched).
- Every dialog shows its available keys in a footer bar.
- Applying from the TUI uses the same writer as the default run: as root, `Enter` on the confirmation validates the plan and writes it; as a non-root uid the TUI writes nothing and prints the `sudo apt-scout --tui` line. Every other Apply rule below holds unchanged.
- Terminal state is always restored on exit, panic or Ctrl-C.

## Apply

- One code path writes, and it is internal. Discovery, verification, rewrite planning and confirmation produce a plan; the plan is validated against the closed target enumeration and the current on-disk state; only then does the first byte change. The plan is never a file, never a message on stdin, and never a flag: the user does not type a step of it, and it does not cross a process boundary. It names files through a fixed enumeration and carries the selected mirror, the verification result that authorizes writing it, the exact bytes, mode, and owner of every file it was computed from, and the exact bytes to write. It carries no freshness baseline: the writer establishes the baseline and holds the selected mirror's proof against it before the first byte. The write aborts, before its first byte, on any missing field, any mismatch with the file on disk, any digest it cannot recompute to the same value, any target that is not a regular file after resolution, and any plan it did not fully validate. The plan binds to the disk by comparing those bytes, not by a hash; every digest the manifest records is SHA-256 over the exact bytes it describes. The write performs no network request of its own, invokes no shell, resolves no command through `PATH`, and reads no environment variable. Never write without root. The confirmation prompt is a safety rail, not a security control: the guarantee is the validation, and `--yes` removes only the prompt.
- Source discovery and inventory are read-only. Scan `/etc/apt/sources.list` and regular `*.list` / `*.sources` entries under `/etc/apt/sources.list.d/`; do not follow symlinks. Report each inspected file and each skipped file/stanza/URI with its reason before mirror probing. If no eligible official archive URI exists, stop before reference/mirror probes: `--list` exits 0, a non-root run prints the `sudo` line and exits 3, and a root run that was going to write exits 1. D7 extracts URI tokens and suites only; it performs no writes.
- Rewrite per URI token, not per file or line. Rewrite a URI when its host is `archive.ubuntu.com`, `*.archive.ubuntu.com`, or any host in the current mirror list (so a previously chosen mirror is recognized without any manifest). Never rewrite `security.ubuntu.com`, `ports.ubuntu.com`, PPAs or third-party hosts. A line or stanza whose suites include a `-security` suite is never rewritten to a probed mirror, even when its host is `archive.ubuntu.com`, because `-security` freshness is not checked; report each skipped entry and why. The only exception is the Pop!_OS split above, which keeps `-security` on the original mirror. On Ubuntu 24.04 and later security already lives in its own stanza (`security.ubuntu.com`), so no split is needed.
- deb822 (`/etc/apt/sources.list.d/*.sources`): a stanza's `URIs:` field may hold several URIs; D7 recognizes continuation lines, repeated fields, comments and stanza boundaries; rewrite only matching tokens in later milestones. Keep every other field (`Types`, `Suites`, `Components`, `Signed-By`, ...) and comments byte for byte. Do not touch stanzas with `Enabled: no`. Missing or malformed `URIs`/`Suites`, duplicate singleton fields, and unknown formats are reported and never guessed.
- Legacy (`/etc/apt/sources.list`, `*.list`): D7 recognizes `deb`/`deb-src` lines, bracketed options such as `[arch=... signed-by=...]`, comments and URI tokens; rewrite only the URI token in later milestones. Malformed lines and unsupported URI schemes are reported and never guessed.
- `mirror://` / `mirror+file:` URIs (older installs): leave unchanged and report them with an explanation.
- Alternatives: in the TUI, the first checked mirror in rank order becomes the active URI. Other checked mirrors are written as commented lines `# alternative: <uri>` above the changed line, so the user can switch quickly. apt has no failover across URIs, so alternatives are documentation only.
- Safety checks before writing: target is a regular file (do not follow symlinks), keep mode and owner, no half-written files.
- File creation is planned, never incidental: `/etc/apt/sources.list.d/system-security.sources` is created with `create_new` and mode 0600, and `EEXIST` aborts the whole apply with nothing written. A planned write that creates a file is accepted only when the platform is Pop!_OS and the target is exactly `sources.list.d/system-security.sources`; a plan that creates any other file, or replaces a file that does not exist, aborts before the first open.
- Backup every file to be changed to `/var/backups/apt-scout/<UTC timestamp>/`, directory mode 0700, refuse a symlinked directory. Write a manifest of original paths. Abort the whole apply if any backup fails.
- Write atomically: temp file in the same directory, fsync, rename.
- `--restore` copies the newest backup back, in one root run: it reads `/var/backups/apt-scout/<backup id>/MANIFEST` itself and aborts before parsing a byte unless that path is a regular file, owned by root, mode 0600, and not a symlink. It then re-derives the target set and every per-target digest from the manifest itself and validates them: every entry matched to the closed target enumeration, every path under `/etc/apt/`, a regular file after resolution, and every recorded digest, mode and owner matching the backup copy it names, refusing the whole restore on the first disagreement; a file the run created has no backup copy, so its record carries the digest, mode and owner the run created it with, and the restore refuses to remove it unless the file on disk still matches. The manifest is the source of truth for what is written, not a list of files the run already chose, so a stale or partial manifest cannot apply a subset of the backup. `--restore` does not depend on the rewrite logic, and it reaches the writer through the same validation as an apply.
- Custom URLs (`Insert`): scheme `http` or `https` only; reject userinfo, whitespace, `file:`, and loopback/private/link-local addresses; probe like any candidate; show a warning before apt is pointed at a user-supplied host.
- If no URI is rewritable (for example arm64, or a system already using a third-party mirror), say so before any probing: scan the sources first, print every file inspected and why each entry was skipped. `--list` exits 0, a non-root run prints the `sudo` line and exits 3, and a root run that was going to write exits 1. Do not probe 30 mirrors for nothing.
- Candidate hygiene (mirror lists are partly fetched over plain HTTP): every candidate, from any list source, must be `http`/`https`, have no userinfo, and not resolve to a private, loopback or link-local address. Results from the `mirrors.ubuntu.com` fallback are marked unverified in the output.
- After apply, suggest `apt update`; do not run it.

## Privilege boundary and threat model

- Security goal: untrusted inputs must not let an attacker execute code as root or write outside the explicitly allowed apt paths through apt-scout.
- Treat CLI arguments/environment, apt source contents, network responses, mirror URLs, backup manifests, file metadata/races, and terminal input as untrusted.
- One process writes, and the accepted cost is stated here rather than hidden. In a root run the networked discovery and the parsing of untrusted responses — geolocation, mirror lists, `InRelease` bodies — happen in the same root process that later writes, because that is the workflow the user chose when running `sudo apt-scout`. What defends the user is the order of operations: nothing is written until the selected mirror's `InRelease` verifies and the internal plan validates against the on-disk state. A two-process split that keeps the network phase out of root is future work and is not a supported flag in v1.
- The write path must use fixed executables/paths and a minimal controlled environment; it must not invoke a shell and must not resolve a command through `PATH`, and after verification it spawns no external process. Validate file type, ownership/mode policy, path containment, and symlink/TOCTOU behavior at the point of use; fail closed on any mismatch.
- The program never re-execs itself privileged, never invokes `sudo`, and is never installed setuid. Privilege is obtained only by the user running the program as root. A root run is the same binary with the same code; the only thing that changes is that it may write. Security review reduces risk but is not a guarantee of absolute immunity.
- What a write is bound to: the bytes it writes are the bytes its own validation passed, over a disk state that still matches the digests it computed. Every target's new content carries a digest the writer recomputes, and a mismatch is refused. The confirmation prompt is a safety rail, not a security control: the guarantee is the validation, and `--yes` removes only the prompt.
- The writer is one code path in one binary, shared by the default run, the TUI confirm, and `--restore`. A separate privileged artifact is out of scope for v1, as is a two-process split; either would be a new product decision, not something a size measurement or a code review finding can trigger.
- Before D9 or any write implementation, D6c, D6e, and D6f must be complete. Every write PR needs a security-focused exact-diff review and disposable Ubuntu-container tests for path traversal, malformed manifests, symlinks/races, backup failures without partial writes, rollback, and rejection of paths outside `/etc/apt`. Never run write tests on the developer host.

## Resilience

Third-party services change formats, add limits or become paid. The program must keep working when they do.

- Geolocation and AS lookups are optional. If country detection fails, the program asks for `--country`; it never silently guesses a worldwide list. If AS lookup fails, ranking proceeds without AS preference. Failures include source and reason.
- Core data comes from sources the project depends on anyway: the Ubuntu archive (`InRelease`), Launchpad mirror list, DNS. No account, key or paid tier is needed anywhere.
- Parsers reject unexpected shapes instead of guessing, and report which field was missing.
- Weekly contract check (`.github/workflows/source-contract.yml` runs `.github/scripts/check-sources.sh`; the script can be run locally; not a required check): fetch each live source once, check that the fields the parser needs are still present, and open an issue only after two consecutive failures (runner IPs can be rate limited by individual services). Scheduled workflows on public repos are disabled after 60 days without repository activity; the check is advisory.

## Errors and self-healing

Principle: the program solves its own problems when safe, and otherwise says exactly what happened, where, why, and what to do. Vague messages ("Unknown error", "Something went wrong", bare `No such file`) are forbidden.

- Every error message states: **what** failed, **which path/URL/value**, **why** (the underlying OS or HTTP error, kept verbatim), and **how to fix** it. Example: `Cannot write /var/backups/apt-scout/: permission denied (os error 13). The path is not writable even as root, which means a read-only mount or an immutable attribute; nothing was written.`
- Error types carry context at the failure point (path, URL, step name); never discard the source error. No `unwrap()` on IO or parsing.
- Self-heal automatically (and tell the user in one line what was done):
  - Missing own cache directory: create with `create_dir_all`. `/var/backups/apt-scout` is created by the writer and verified after creation to be a directory, owned by root, mode 0700, and not a symlink; a pre-existing path that fails any of these is a hard abort with nothing written.
  - Missing, empty or corrupt cache file: ignore it, refetch, rewrite it.
  - Missing `/etc/os-release`: try `/usr/lib/os-release`, then `lsb_release` fallbacks; if still unknown, ask for `--codename`/`--distro` flags.
  - Missing `UBUNTU_CODENAME` and `VERSION_CODENAME`: use the codename in the existing apt sources, then ask for `--codename`.
  - Apt sources at an unexpected location or format: search `/etc/apt/sources.list`, `/etc/apt/sources.list.d/*.{list,sources}`, and report every file inspected and why each was skipped or used.
  - Network failure: follow the mirror-list source chain, retry, then use cache/snapshot; report each failed source with its reason.
  - Interrupted write: temp files are cleaned up on the next run; the original file is never left half-written.
- Do not self-heal when it is unsafe: never guess which apt file to overwrite, never continue after a failed backup, and self-healing never creates a file in `/etc/apt`. That last prohibition is about self-healing, not about planned writes: the only file apt-scout ever creates there is the planned `sources.list.d/system-security.sources` on Pop!_OS (see Apply), which comes from the validated plan and is opened with `create_new`. Stop and explain instead.
- No silent fallbacks: whenever a fallback is used, print which one and why.
- Exit codes (see Non-functional) always accompany a message that explains the cause.
- Tests cover the message content for the common failures (missing dir, permission denied, corrupt cache, unreachable network, unknown distro).
- Docker integration tests for source discovery/apply/restore must use disposable Ubuntu containers and isolated `/etc/apt` fixtures. Never mount or mutate the developer host's `/etc/apt`; test rollback, manifest path validation, permissions, and byte-exact restore in the container. Write tests cover: a non-root run writing nothing and exiting 3, a root write aborting before its first byte on a failed validation, symlinked targets and a symlinked `sources.list.d`, substitution between validation and write, a target whose recomputed digest does not match the bytes to be written, a restore whose manifest is stale, partial, or names a path outside `/etc/apt`, a read-only `/etc/apt` mount, backup failure aborting before any write, byte-exact restore of content/mode/owner, hostile `PATH`/`HOME`/`TMPDIR`, a pre-existing `system-security.sources` aborting the apply, and a write that still succeeds when `/usr/bin/gpgv` is removed after verification has already happened (test hook), proving the write does not re-verify.

## Non-functional

- Static musl binary. `ureq` with rustls, `ratatui` + `crossterm` for the TUI. No async, no OpenSSL.
- All output, errors and docs in English.
- Ship a comprehensive Linux man page at `man/apt-scout.1`, accessible as `man apt-scout`. It documents only implemented behavior and covers SYNOPSIS, options/modes, security/privacy, files, errors, exit status, practical command examples, and usage recipes. Install it in `.deb` as `/usr/share/man/man1/apt-scout.1` and include it in the release `.tar.gz` with installation instructions.
- Exit codes: 0 ok, 1 runtime error, 2 usage error, 3 the run would write and this uid may not — every non-root run other than `--list` that reaches the write, which prints the command to run instead; a usage error (2) and a failure earlier in the run (1) keep their own code; 4 unsupported distro or architecture. A root run that found no eligible or no rewritable source writes nothing and exits 1, as Apply states; `--list` exits 0 whatever the uid and a non-root run exits 3.
- Milestones: (1) read-only distro, geo, mirror list, probe, freshness, rank, and CLI — complete (PRs #13–#16); (2) apt source discovery/rewrite, apply, backup, and restore — in progress (D7 inventory and D8 pure rewrite plan complete; D6c signature verification and its D6f follow-up merged as PRs #25 and #29); (3) TUI core flow and user laptop terminal inspection; (4) TUI `Insert`/`Delete`. The execution sequence, task status, dependencies, PRs, and milestone audit gates live in `ROADMAP.md`.
- Suggested layout: `main.rs`, `error.rs`, `distro.rs`, `geo.rs`, `mirrors.rs`, `probe.rs`, `fresh.rs`, `verify.rs`, `rank.rs`, `sources.rs` (pure string in/out), `apply.rs`, `tui/`. Keep `sources`, `rank`, `fresh` pure; HTTP is injected as a function so tests use canned responses.
- Test fixtures: Ubuntu 22.04 `sources.list`, 24.04 `ubuntu.sources`, multi-URI stanza, `Enabled: no`, comments, `deb-src`, arm64 ports, `InRelease`, mirror list HTML and text, corrupt cache. D7 tests read-only source inventory/parsers; D8 tests byte-preserving rewrite output and URI round trips. Later apply milestones add restore-equals-original, tempdir atomic write, and failed-backup-abort tests. TUI uses `ratatui` `TestBackend` snapshots.
- Parsing and ranking are pure functions, unit-tested on fixtures; no live network in tests.
- Security note: all geolocation and AS answers are untrusted input, validated, and influence ranking only. Canonical's lookup is plain HTTP; AS data comes from DNS. Nothing derived from them is ever written into apt sources.
- Freshness trust boundary: ranking may display and use an `InRelease` `Date` even when signature verification is `invalid` or `unavailable`; this can mis-rank a mirror but cannot authorize package installation. Every `-updates` `InRelease` used by probing is verified with `/usr/bin/gpgv --keyring /usr/share/keyrings/ubuntu-archive-keyring.gpg`, using no shell, no `PATH` lookup, a cleared environment, a private 0700 temporary directory that is also `gpgv`'s `--homedir` (so no user GnuPG configuration or default home can influence the result), a 10-second process timeout, and a 1 MiB cap on captured status output. The download cap is the verifier's own 512 KiB cap, so an oversized file is rejected at download instead of being reported as an unverifiable but rankable mirror. The informational `-security` pocket is read as a ranged head of 4 KiB and is never verified, because nothing consumes its signature. Missing/invalid `gpgv` or keyring, unsigned/changed/unknown-key data, oversize data, and execution errors are shown explicitly and are never `Verified`. Only a `Date` from inside the cleartext-signed region (step 8) is ever trusted: bytes before `-----BEGIN PGP SIGNED MESSAGE-----` or after `-----BEGIN PGP SIGNATURE-----` are outside what `gpgv` signs, so a `Date` read there is shown and ranked, is never a verified date and never authorizes a write. Ranking may use a `Date` whose status is `invalid` or `unavailable`, but only a `Verified` `Date` parsed inside the signed region is usable by a write. Before a write may use a ranked mirror, the selected mirror's `-updates` `InRelease` and the write baseline must both be `Verified`. Ranking has a separate baseline that ignores verification and may fall back to the newest candidate `Date`, verified or not. The write baseline may not ignore verification: it is the canonical reference when that reference's own `verified_updates()` is `Some`, and otherwise the newest candidate whose own `verified_updates()` is `Some`; when neither the canonical reference nor any candidate yields one, a write fails closed. Trusted freshness dates are represented by a value that only a `Verified` status can construct (`VerifiedDate`), and the probe result, the reference and the ranked entry each expose it, so a write path takes that value and never a bare `Date`. If verification is not available, write mode fails closed while read-only ranking still works. `VerifiedDate` protects the date half only: it wraps a `fresh::SignedDate`, which only the strict in-region parser builds, so no write path can be handed a `Date` read outside the signed region. It does not protect the status half: `SignatureStatus::Verified` is a public variant any crate path can construct without running `gpgv`, and `ROADMAP.md` carries no task that makes it unforgeable, so the value proves where its `Date` was read, never that `gpgv` approved the body. `.deb` packages must depend on `gpgv` and `ubuntu-keyring`; tarball instructions must name them.

## Testing

- Unit tests (`#[cfg(test)]`) cover pure logic on fixtures: `os-release`, Launchpad HTML, `mirrors.txt`, `InRelease` dates, freshness, ranking, read-only apt source inventory/parsers, and D8 source rewrite output/round trips. Saved fixtures come from real responses (the Launchpad page is ~316 KB; keep a trimmed copy with at least two countries and every status value seen).
- Docker integration tests run inside disposable real Ubuntu images; offline cases and live-network smoke cases are both included. Live cases require internet and are manual, never part of CI. The matrix covers every supported release; format measured on 2026-11-11:

  | Release | Codename | Sources format |
  | --- | --- | --- |
  | 20.04 | focal | legacy `/etc/apt/sources.list` (10 `deb` lines) |
  | 22.04 | jammy | legacy `/etc/apt/sources.list` |
  | 24.04 | noble | deb822 `/etc/apt/sources.list.d/ubuntu.sources` |

A forged body is built in the test from the signed fixture by prefixing a `Date:` line, so the regression proves all three facts at once: the prefix verifies under `gpgv`, the signed-region parse yields no date for it, and read-only ranking still uses the displayed date. Unit tests that need a real `gpgv` and keyring skip when `/usr/bin/gpgv` or the archive keyring is absent (developer hosts), and the Docker cases are the end-to-end proof of the positive path. Releases whose reference `InRelease` returns 404 are handled by the exit-4 rule in step 8. `focal-updates` was still receiving updates on 2026-11-11 (`Date` 2026-11-11), so freshness stays meaningful for 20.04; keep a focal fixture. `i386` is in scope but covered by fixtures only (no i386 image). The `amd64` images are used (`--platform linux/amd64`); on Apple Silicon they run under emulation, slower but equivalent. Current Docker tests cover distro detection, read-only inventory/early stop, live mirror ranking, the missing-`gpgv` case (every signature reads `unavailable (<reason>)` while ranking and the exit code stay usable), and one live case that requires a real `verified` reference and at least one `verified` mirror row after installing the two `.deb` dependencies, because a base image is not a package install.
