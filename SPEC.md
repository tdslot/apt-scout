# apt-scout SPEC

Standalone Rust CLI. Picks the fastest, fresh, nearby Ubuntu archive mirror and rewrites apt sources. Equivalent of `nala fetch` without installing nala. No Python or other runtime.

## Scope (v1)

- Ubuntu and derivatives, detected from `/etc/os-release` `ID` / `ID_LIKE`. The codename is `UBUNTU_CODENAME` when present, otherwise `VERSION_CODENAME`: Linux Mint reports `VERSION_CODENAME=wilma` but apt uses Ubuntu's `noble`.
- Pop!_OS (`ID=pop`, `ID_LIKE="ubuntu debian"`, `UBUNTU_CODENAME` equals the Ubuntu base, for example `jammy`): supported. Verified from the real `pop-default-settings` package (`/etc/pop-os/os-release`, `postinst`): the active source is the deb822 file `/etc/apt/sources.list.d/system.sources` with `URIs: http://apt.pop-os.org/ubuntu`, `Suites: <codename> <codename>-security <codename>-updates <codename>-backports`, and `X-Repolib-Default-Mirror: http://apt.pop-os.org/ubuntu`. `apt.pop-os.org/ubuntu` is a true Ubuntu mirror (`Origin: Ubuntu`, same `InRelease` Date as `archive.ubuntu.com`). Rewrite rules for Pop!_OS: rewrite only the `URIs` of `system.sources`; leave `X-Repolib-Default-Mirror` unchanged (it is the vendor default kept for restore, as `apt-manage` treats it); never touch System76's own repositories (`apt.pop-os.org/release`, `apt.pop-os.org/proprietary`, `pop-os-apps.sources`). `apt.pop-os.org/ubuntu` is treated as an official archive URI for Pop!_OS only. Because Pop!_OS keeps `-security` in the same stanza as the other suites, the rewrite moves it: `system.sources` keeps the non-security suites with the new mirror, and a new file `/etc/apt/sources.list.d/system-security.sources` holds a stanza for the `-security` suite on the original mirror (this is the one case where apt-scout creates a file in `/etc/apt/sources.list.d`; it is recorded in the backup manifest and removed by `--restore`). The new stanza gets a different `X-Repolib-Name` (`Pop_OS Security`) and copies `Types`, `Components`, `Enabled` and `Signed-By` from the original. Verified in a container with the real repolib 2.2.2 package: two stanzas with the same `X-Repolib-Name` in one file are merged on `load()`+`save()` (the first stanza gains the `-security` suite), so splitting inside one file is unsafe; separate files with different names load and save unchanged. The pure D8 transformation returns both the rewritten `system.sources` content and the planned new `system-security.sources` content without filesystem IO; D9 owns file creation, backup and atomic write. The diff shows the split before anything is written. `repolib`/`apt-manage` may add `X-Repolib-ID: system` on save; that is harmless. Tools such as `pop-upgrade` or `apt-manage` can later reset the URIs to the vendor default; the rewrite is then simply undone, which is acceptable. Check whether the `pop-default-settings` `postinst` overwrites `system.sources` on package upgrade (it only creates the file when missing, so an upgrade does not overwrite it).
- Debian: out of scope (different mirror list). Unsupported distro -> exit with clear error.
- Only official Ubuntu archive URIs are rewritten (and `apt.pop-os.org/ubuntu` on Pop!_OS). `security.ubuntu.com`, PPAs, third-party repos are never touched.
- Architectures `amd64` and `i386` only (from `dpkg --print-architecture`). Other architectures (arm64, ...) use `ports.ubuntu.com`, which has no mirror choice: print an explanation and make no changes.

## CLI

Single command, no subcommands: `apt-scout [flags]`

No flag is required. The uid decides whether the run writes: it discovers, ranks and recommends, and a non-root run prints the one line that repeats the run under `sudo` and exits 3, while the same command under `sudo` writes the best mirror. Every flag below is an override, never a step in the workflow.

A short form exists for every flag that is implemented today: `-a`, `-c`, `-n`, `-s`, `-t`, `-v`, `-l`, `-y`, `-r` and `-h`. `--no-color` is the one implemented flag without a short form. `-R` stays reserved for `--refresh` and is rejected until that flag exists. Short flags are never bundled: `-lyc NO` is an unknown option. The line a non-root run prints always spells the long forms, so a copied command is unambiguous.

| Flag | Meaning |
| --- | --- |
| `-c`, `--country <CC>` | ISO 3166 alpha-2 override. Always wins over detection. |
| `-a`, `--any` | Ignore the detected and the given country: consider the mirrors the list names for **every** country and rank them together. The country is then display-only. `--any` with `--country` is not an error — the country simply stops constraining the candidate set. Needs no country at all, so it also satisfies `--no-geo`. |
| `--refresh` | Ignore the geo, mirror list and AS caches for this run (and rewrite them). |
| `-n`, `--no-geo` | No geolocation lookups at all. Requires `--country`, or `--any`, which needs no country; AS preference is skipped. Offline-friendly for the server lookup. |
| `-t`, `--top <N>` | Show N best mirrors (default 5). |
| `-s`, `--https-only` | Only consider https mirrors. |
| `--tui` | Interactive mode: ranked table, selection, detail panel, confirmation. Opt-in; the default run is not interactive. |
| `-l`, `--list` | Table and planned change only; never writes, whatever the uid. |
| `-y`, `--yes` | Skip the one confirmation before a write in a root run. |
| `-r`, `--restore` | Restore the newest backup instead of applying a mirror. Root is needed for the read of the backup and for the write. |
| `-v`, `--verbose` | The proof behind the default report (Output): each row's AS number and same/`diff`/`unknown` match, the server's AS, each row's country and the address the run resolved, both pocket dates in full, the `-security` lag, the exact signature status, a redirect host in full, and the full text of every rejection reason. Display only; it changes no decision. |
| `--no-color` | No colour in the report, whatever the terminal is. Display only; Output states the rules. No short form. |

Command, uid, and whether apt sources change:

| Command | uid | Writes apt sources |
| --- | --- | --- |
| `apt-scout` | non-root | No: discovery, ranking, the recommendation with its reason, the one line `sudo apt-scout`, exit 3. |
| `sudo apt-scout` | root | Yes: the same discovery and recommendation, one confirmation (`--yes` skips it), the write. |
| `apt-scout --list` | any | No: the ranked table and the change a write would make, exit 0. |
| `apt-scout --tui` | non-root | No: the interactive selection, then the one line `sudo apt-scout --tui`, exit 3. |
| `sudo apt-scout --tui` | root | Yes, on the confirmation dialog: the selection the user arranged is written. |
| `apt-scout --restore` | non-root | No: the one line `sudo apt-scout --restore`, exit 3. |
| `sudo apt-scout --restore` | root | Yes: the newest backup, after one confirmation (`--yes` skips it). |

Behavior by mode:
- Every run of the mirror pipeline prints the ranked table, then the recommendation and its reason: host, the mirror's own country, how far `behind` it is, speed, `latency` and signature status. The country in that line is the selected mirror's, not the run's, because the two differ once a run is not narrowed to its own country. The chosen mirror's AS, and whether it matches the server's, are `--verbose`'s and the default recommendation does not name them (Output). Rejected mirrors are listed with the reason they were rejected. A run whose candidate set was widened (Pipeline 4) prints one `note:` line under the report header, before the table, saying why; a run given `--any` says in the header's country field that the country does not constrain it. Neither statement is opt-in and neither can be turned off.
- A write confirms once: the files it will change, the old URI and the new one, and the backup path it will create. It does not repeat what `Sources` already reported as skipped. `--yes` skips that prompt. The prompt is a safety rail, not a security control: the guarantee is the validation described in Apply, and no answer to the prompt can bypass it.
- A non-root run without `--list` prints the table, the recommendation and one line, then exits 3: `sudo apt-scout` with the flags of that run repeated. It opens no apt file for writing.
- `--tui` is opt-in and is never chosen for the user. The default run is non-interactive, so no flag turns the TUI off.
- `--restore` replaces the source of the rewrite: the newest backup instead of the mirror pipeline. Root is needed for that read as well as for the write, so the non-root run prints only `sudo apt-scout --restore` and exits 3 before it opens the backup. Its confirmation names the backup it reads, the files it writes and the backup it creates, instead of the old and new URI an apply's confirmation shows, because a restore's plan carries bytes and no URI pair. `--list` with `--restore` is a usage error (exit 2), refused before the backup is opened: a non-root run could not read the root-only manifest to show anything, and a root run's own confirmation names the same files and backups. A restore runs nothing of the mirror pipeline, so it is refused in the same way with `--country`, `--any`, `--top`, `--https-only` and `--no-geo`, each a usage error (exit 2) naming the offending flag; `--yes` is the unattended form, and `--verbose` and `--no-color` are display only. The block a finished restore prints is its own, under a `Restore` heading rather than the mirror report's sections: the backup it put back, each file it wrote and each file it removed, and the backup it created for what it replaced, and `--verbose` adds each file's digest, mode and owner. A restore the confirmation cancelled (nothing was written) exits 0: that answer is the user's decision, not a failure, and only an apply refuses a no, because there the write is the point of the run. The block names the backup that was put back, taken from the plan the confirmation printed, because the plan a run prints is the plan it writes: no step re-derives it after the answer.
- No step of the write is a mode the user types. Building the plan, validating it against the closed target enumeration and the current on-disk digests, verifying the mirror's `InRelease`, and writing are one code path inside the program (see Apply); the plan never crosses a process boundary and is never a file.

## Output

- **The default report is the decision; `--verbose` is the proof.** The default report answers "which mirror should I use and why" and `--verbose` answers "prove it to me", so a fact is in the default report only when a person choosing a mirror acts on it, and a fact that only lets a reader check the run is `--verbose`'s. Nothing below is optional and nothing below is a flag of its own: `-v` is the one switch, and it adds to the default report instead of replacing any part of it. Every one of these is `--verbose`'s alone, and the default report carries none of it: each row's AS number and its `same`/`diff`/`unknown` match with the server, and the chosen mirror's in the recommendation; the server's AS on the context line, which keeps its `mirrors:` and `reference:` fields; each row's country and the address the run resolved for it; both pocket dates in full, `-updates` and `-security`, and the `-security` lag; the exact signature status instead of the table's `yes`/`no`/`?`; a redirect host in full instead of the cut form; the full text of every rejection reason instead of the grouped class and its count. The default report keeps the identity line, `Sources` with its rewrite and skip reasons, the context line without the server's AS, the table, the recommendation, the planned change with the backup path, and the `Rejected` counts grouped by class. `--verbose` is display only in the same sense colour is: it reaches no decision, no ordering, no path, no byte written and no exit code, so two runs that differ only in it probe, rank, plan and write identically.
- **The ranked table's columns are named for what they measure.** `behind` is how far the mirror's `<codename>-updates` package lists trail the freshest date the run knows: minutes, `0m` when the mirror is up to date, and the same number Pipeline 8 rejects against, so it is freshness and never network latency. `latency` is the measured round trip of the mirror's `-updates` request, time to first byte as Pipeline 7 defines it, and never freshness. `verified` is the `<codename>-updates` `InRelease` signature: `yes` when `/usr/bin/gpgv` accepted it with the Ubuntu archive keyring, `no` when the body was readable but unsigned, altered or signed by an unknown key, and `?` when verification could not run at all — a missing `gpgv` or keyring, an oversized body, or a timeout. Only `yes` may authorize a write; `no` and `?` never do, and neither is a reason to reject or reorder a row, because read-only ranking keeps its tolerance (Freshness trust boundary). The legend printed with the `Ranked` title states one clause per column that needs one — `behind = -updates age vs freshest · latency = round trip · verified = InRelease signature` — and the recommendation uses these same words, never a second spelling of the same fact.
- **One report, one block.** A run writes its report once, on stdout, once probing and ranking are done: the identity line, `Sources`, the ranked section with its title, `Detail` in a `--verbose` run, `Recommendation`, `Planned change` when the mode plans one, in that order, and `Rejected` only when something was rejected. The identity line and `Sources` are always there; a section after them is printed when the run reaches it, so a run that stops before probing has neither. Nothing a run prints while it works can split the report. A section with nothing to say prints nothing at all — no heading, no `0` count — and every fact a section carries is the fact `CLI`, `Pipeline` 7–9 and `Apply` name, never a second copy of a fact another section has already printed. What a write prints after the confirmation (`backup:`, `wrote`, `changed`) is a second block, which this section does not change.
- **Colour is display-only.** Colour appears only when stdout is a terminal, `NO_COLOR` is not set (any value counts as set, the empty one included) and `--no-color` was not given; in every other case the run prints no escape sequence at all. Where it is on: section headings and the identity line are bold; in the table `yes` is green and `no` and `?` are yellow; a rejection reason and a `-` diff line are red, a `+` diff line is green; the `behind`, `speed` and `latency` column headings are dim; the recommended mirror and the confirmation prompt are bold. Nothing else is styled, and the `sudo apt-scout …` line a non-root run prints is never styled, because a user copies it.
- **The plain output is the contract, and colour reaches no decision.** With colour off the report carries the same words, the same columns and the same section headings a colour run prints, minus the escapes, so a harness that captures stdout matches the same lines either way: the container matrix runs with stdout a pipe, therefore colour off, and asserts that text. Colour is never an input to a decision, a comparison, an ordering, a path, the plan, the bytes written or an exit code, so two runs that differ only in colour write the same bytes under `/etc/apt` and exit with the same code.
- **Progress is transient, animated, and only for a person.** While a run works it shows one status line, on stderr, rewritten in place, and only when stderr is a terminal; when stderr is a pipe, a file or a CI log, no progress line is written at all — no timestamped line, no "still working" notice — and nothing is started to draw one. The line is **animated**: one Braille cell, advanced one frame about every 100 ms by a ticker for as long as a phase is active, so a phase that runs for five seconds is visibly moving instead of a still line that changes only when a count does. The phases it names are loading the mirror list, verifying the reference, probing, which carries `n/m`, the candidates probed so far, and ranking; the probing count renders inside the same frame as the cell, so one line carries both and neither is a second line. A warning keeps its own line on stderr: a progress rewrite never overwrites one, a warning never carries a progress line, and the animation is stopped while a warning is on screen and resumes with the next phase. The ticker advances a frame and redraws the line it is given and does nothing else: no probe's timeout, request, measurement, rejection or join order changes because a frame was drawn.
- **The animation is testable without a terminal, and it adds no dependency.** The frame is a pure function of the time a phase has been active, and the ticker's loop is driven through the existing progress `Sink` seam with an injected wait, so a synthetic 300 ms phase asserts the frames that were drawn and the text they carried, with no sleep, no thread and no terminal in the test. The animation is standard library only — `std::thread`, `std::sync::mpsc`, `std::sync::Mutex`, `std::time` — so no terminal crate, no progress crate and no new dependency is added, and a sink write that fails is dropped as before rather than turned into an error.
- **Progress ends with one summary line.** The ticker is stopped and the live line cleared before the report is printed, and no frame may be drawn after that: the status line is replaced by `done — <usable> usable, <rejected> rejected in <t> s`, with one decimal place, for example `done — 4 usable, 0 rejected in 3.1 s`. The counts are the ones the ranked title carries, and the time runs from the loading phase to the end of ranking; no transient line and no ticker outlives the report's first line.
- **`NO_COLOR` and, later, the locale are the only environment reads that may change printed text.** `NO_COLOR` is a display-only read and the locale read of Localization is the other: neither reaches a decision, a path, a byte written or an exit code, and no module reached from `src/apply.rs` reads either.

## Pipeline

1. **Detect distro** from `/etc/os-release`. Read the codename: `UBUNTU_CODENAME` when present, otherwise `VERSION_CODENAME` (Linux Mint reports `VERSION_CODENAME=wilma`, but apt uses `noble`).
2. **Detect location** of the server (country, then AS), skipped with `--no-geo`. Every source is optional: if all fail, the program asks for `--country`, or for `--any` where no country is needed; it does not guess a worldwide list. The mirror-list sources themselves are Launchpad for the selected country, then the `mirrors.ubuntu.com` country list. Sources are tried in order and the first valid answer wins; web sources use HTTPS except Canonical's endpoint noted below; AS comes from DNS.
   1. Country: Canonical `http://geoip.ubuntu.com/lookup` (XML, field `CountryCode`; the same endpoint the Ubuntu installer uses; plain HTTP, so treat the answer as untrusted and validate it). Fallbacks: `https://ifconfig.co/json` (`country_iso`, operator asks for at most 1 automated request per minute), `https://ipinfo.io/json` (`country`), `https://www.cloudflare.com/cdn-cgi/trace` (`loc=<CC>`).
   2. AS of the server: Team Cymru DNS, TXT query for `<reversed-ip>.origin.asn.cymru.com` (IPv6: `<nibble-reversed-ip>.origin6.asn.cymru.com`; answer `AS | prefix | CC | registry | date`; the `CC` is the registry country, not a location, so it is never used as the server country). No web API and no HTTP: plain DNS through the system resolver. Fallback in the current implementation: the already-fetched `ifconfig.co` or `ipinfo.io` `asn`/`org` fields. RIPEstat is planned, not yet implemented.
   - To query Cymru the server's public IP is needed: take it from whichever HTTP source answered (geoip, ifconfig.co, ipinfo, Cloudflare `ip=`). If none answered, AS is unknown.
   - No retries: any failure (timeout, non-200 including 429, malformed body, DNS error) falls through to the next source. HTTP requests use a 10 s whole-request timeout, including redirects. Geolocation responses are capped at 256 KiB; the mirror-list page has a 2 MiB cap. The maximum chain duration depends on which sources fail and whether later AS queries are needed; AS DNS lookup has a 12 s total per-query budget and mirror-AS ranking has a 20 s overall budget. Print which sources failed and why.
   - Validation: country is uppercased and must match `^[A-Z]{2}$`; `XX` (unknown), `T1` (Tor) and `Unknown` are treated as unknown. The same rule applies to `--country`.
   - AS normalization: every source's value becomes canonical `AS<number>`. Take the first whitespace-delimited token of `org`/`as`, prefix bare integers with `AS`, validate `^AS[0-9]{1,10}$`, compare numerically. Empty or malformed means unknown. For a prefix with several origin ASNs the first listed is used; this is approximate.
   - `--country` overrides the country only; AS is still looked up unless `--no-geo`.
   - Cache is planned, not yet implemented.
   - Privacy: live geolocation web services learn the server's public IP; system DNS and Team Cymru receive the IP inside a DNS query. Candidate mirror host IPs are sent to DNS and Team Cymru for AS lookup. `--no-geo` skips all these lookups and requires `--country`.
   - `--country` replaces only the country answer; the chain still runs to learn the public IP for the AS lookup unless `--no-geo`.
**Preflight before any network access:** validate CLI country values against the supported country table and validate the local architecture. Invalid country/unsupported architecture must fail before geolocation or any HTTP/DNS request. Resolve this before invoking geo or mirror-list sources.

3. **Load mirror list**, first success wins, source shown in output:
   1. Launchpad `https://launchpad.net/ubuntu/+archivemirrors` (HTML, ~316 KB, ~560 mirrors in ~80 countries). Measured structure: a `<tr class="head">` row with `<th colspan="2">Country</th>` starts each country; each mirror row has a `/ubuntu/+mirror/<id>` link, one `<a href>` per protocol (`https`, `http`, `ftp`, `rsync`; only `http(s)` are used), a speed (`10 Gbps`), and a status `<span class="distromirrorstatus{UP|UNKNOWN|...}">`. Launchpad's own status (`UP` = up to date) is used as a hint, never as proof of freshness. Measured: 82 country sections, 562 mirror rows, only `UP` and `UNKNOWN` statuses seen, speeds from `128 Kbps` to `100 Gbps`, and 2 rows with only `ftp`/`rsync` links (skip them, they cannot be probed over HTTP). The parser must tolerate missing protocols and unknown statuses, and is tested against a saved fixture of this page.
   2. `http://mirrors.ubuntu.com/<CC>.txt` (plain text, one URL per line, already ordered by geographic proximity, ~6 URLs, no speed or status). Used when Launchpad fails or returns no mirror for the country. One country's file per run: `mirrors.txt` holds one line, `http://archive.ubuntu.com/ubuntu/` (measured 2026-11-13), so it is not a wider source, and no run fetches another country's file.
   3. Disk cache `~/.cache/apt-scout/mirrors.json` (valid 24 h; stale cache used only if all else fails, with a warning)
   4. Snapshot compiled into the binary (dated; warn when older than 90 days)

   Each network source: one 10 s time budget per call covering redirects (no retries in v1: a failure falls through to the next source), response validated (non-empty, at least one well-formed `http(s)://` URL; for Launchpad, at least one country section). Invalid response counts as failure.
4. **Filter**: mirrors in the detected country only, unless `--any` is given, which removes the country from the candidate set; plus the one automatic widening described below, which adds every other country's mirrors once and only when the run's own country came back with nothing usable. Candidates are deduplicated (ignoring a trailing slash and case), capped at 30, and `--https-only` drops http. This filter narrows candidates only: every mirror host the Launchpad page names, in every country, stays eligible for replacement under Apply's rewrite rule, and `--https-only` does not narrow that set. An unknown country code (not one of Launchpad's 82 countries) is a usage error (exit 2) before any network request; it does not fall back to `mirrors.ubuntu.com/<CC>.txt`.
   - `--any` (`-a`): every mirror the loaded list names enters the candidate set, whatever country the list puts it in, and they are ranked together as one set. The country is display-only: the run still detects it or takes it from `--country`, prints it, and says it is not a constraint, and it decides nothing else. `--any` with `--country` is therefore not an error. `--any` needs no country at all, so with `--no-geo` it satisfies the country requirement, the `<CC>.txt` fallback then has no file to read, and only Launchpad can supply the list; a list that names one country is reported as one country, never presented as every country. The match and tie-break of step 9 are unchanged, so AS preference still applies when the server AS is known.
   - **Automatic widening, once, from an empty set only.** When every candidate in the run's own country is rejected — stale, unreachable, non-200 including 404, no usable `InRelease` or `Date`, no speed sample, or a crashed probe — the run adds the mirrors the same list names for every other country, probes those in one extra pass, ranks them together with the country's own results, and prints one `note:` line under the report header saying why it widened. It does not exit with an error. It is never a preference and never a top-up of a set that has a usable mirror: a run that found one usable mirror in its own country never widens, and no candidate is probed twice. A widened run that finds a mirror exits as any run does — 0, or 3 for a non-root uid that would have written; a widened run that finds nothing fails exactly as it did before, with the no-fresh-mirror message and exit 1. `--any` never widens: its set is already every country, so an empty one means nothing usable anywhere.
   - Widening reuses the list the run already loaded and never fetches a second one. Launchpad names every country, so it can widen. `mirrors.ubuntu.com/<CC>.txt` names one country per run and no run fetches another country's file (step 3), so a run whose only list is that file cannot widen: it prints a line saying so and fails exactly as before. A widened set is therefore always drawn from a list fetched over HTTPS.
   - The 30-candidate cap applies to a set that is not narrowed to one country, and there it is applied by Launchpad's own declared link speed, descending, then by URL: the page names about 560 mirrors, and probing them all is not a burst any run makes. That prefilter decides what is probed and never what ranks — a mirror whose declared speed is unknown sorts last among the candidates and still ranks wherever its probe puts it. A run narrowed to one country keeps the cap in list order.
5. **Resolve AS** of candidates (skipped with `--no-geo`; informational, never a reason to fail the run): resolve each hostname to an IP, then Team Cymru DNS TXT per IP (parallel, cap 8 at a time), normalized as in step 2. No per-IP fallback is implemented yet; failures leave AS unknown. Cymru client: hand-rolled raw UDP query (about 80 lines; std has no TXT API and an async resolver crate contradicts the no-async rule). Read nameservers from `/etc/resolv.conf` (up to 3; the systemd-resolved stub `127.0.0.53` and Docker's `127.0.0.11` handle TXT), use an absolute name with a trailing dot (no search-domain expansion), connect the UDP socket, use a transaction ID, validate the reply ID and `QR` bit, cap compression-pointer traversal, treat NXDOMAIN as AS unknown, and treat the `TC` (truncated) bit as failure (no TCP fallback). Missing `resolv.conf` means AS unknown. No HTTP batch API and no rate-limited free tier is required. AS caching is planned, not implemented. CDN-backed mirrors can resolve to different AS per query; AS is approximate. Current implementation resolves the first address returned by the system resolver; IPv6-specific candidate selection is not implemented yet.
6. **Fetch reference** once, before probing: from `http://archive.ubuntu.com/ubuntu/dists/<codename>-updates/InRelease` and `<codename>-security/InRelease` get the `Date:` of each pocket. The `<codename>-updates` reference is downloaded in full under the 512 KiB download/verification cap and its OpenPGP signature is verified, and both its `Date` and its signature status are kept, because it is the freshness baseline a write may trust. The `<codename>-security` reference is a ranged 4 KiB head and is never verified, because nothing may consume its signature. This is the freshness baseline. The `<codename>` release pocket is not compared: its `Date` is the release date (for example `noble` shows April 2024) and never changes, so it says nothing about freshness.
7. **Probe** each candidate in parallel (`std::thread`): fetch `<mirror>/dists/<codename>-updates/InRelease` in full under the 512 KiB download/verification cap so its OpenPGP signature can be checked, and fetch only the head (`Range: bytes=0-4095`) of `<mirror>/dists/<codename>-security/InRelease` for the informational `Date`. Measure time to first byte (DNS, TCP, TLS and one round trip) on the `-updates` request, never the body download time. Measure throughput on a larger sample (`Range: bytes=0-1048575` of `main/binary-<arch>/Packages.xz`), because the ~130 KB `InRelease` is too small and too variable to measure throughput. Redirects: follow at most 3, re-validate the final host and scheme; report mirrors that redirect to another host.
8. **Reject** unreachable mirrors, non-200 responses, and stale mirrors. `<codename>-updates` decides: a mirror is stale if its `Date` is older than the reference by more than `MAX_LAG` (24 hours). `<codename>-security` lag is shown for information only, because `security.ubuntu.com` is left untouched. A missing `-updates` pocket or unparsable `Date` rejects. A `Date:` is trusted only when it is inside the cleartext-signed region: nothing but whitespace-only lines may precede `-----BEGIN PGP SIGNED MESSAGE-----`, which must itself start its line (`gpgv` refuses a space-prefixed armour header), the armour headers that follow it are skipped up to the first blank line, and the search stops at `-----BEGIN PGP SIGNATURE-----`. A body with any other content before the armour header, or with its only `Date:` after the signature header, still has a good signature: `gpgv` accepts such a prefix, so its signature status is `verified` and is displayed as such, and naming it `invalid` would change what the status means. What such a body cannot supply is a trusted `Date`: a `Date` read outside the region is never a verified date, never a write baseline and never authorizes a write, because a write takes only a date parsed inside the region, so the parser, not the verifier, separates a signed `Date` from a displayed one. Read-only ranking keeps its tolerance: a `Date` read outside the signed region is still used for lag, ranking and the table, so a mirror that serves one is ranked, not rejected. An `InRelease` larger than the 512 KiB download/verification cap is rejected at download, because the verifier would refuse it anyway. That oversized rejection applies in read-only mode too: the promise that read-only ranking still works covers a missing or unusable `gpgv`, not a mirror that sends more than the cap. `Date` is the signing time, not the sync time. If the reference host is unreachable (network error, 5xx), use the newest `Date` among candidates as baseline and print a warning; a `Date` more than `MAX_LAG` ahead of the median is treated as bogus and ignored, so one wrong clock cannot make every other mirror stale. Only the `<codename>-updates` reference decides whether the release left the archive; an unreadable `-security` reference is ignored (it is informational). If the reference answers 404 for the codename, the release is no longer on `archive.ubuntu.com` (it moved to `old-releases.ubuntu.com`, which has no mirrors): exit 4 with a message that names the codename and explains this; never use the newest-candidate baseline in that case. Measured on 2026-11-11 (`noble-updates`): of 10 Lithuanian and Norwegian mirrors, 6 matched the reference exactly and 4 were identical to each other but one signing generation behind (about 6 hours), so a 1-hour limit would reject 40% of good mirrors. Freshness also guards against replay of old indexes; apt still verifies signatures.
9. **Rank**: compare `-updates` `Date` exactly (no tolerance); lag is the reference `Date` minus the mirror `Date`, clamped to 0 because the reference is fetched first and a mirror may be newer. Primary key: lag ascending (mirrors with equal `Date` form one group). Within a group: throughput descending, then latency ascending; a mirror in the same AS as the server wins when its throughput is within 20% of the group's fastest mirror (band measured against that top speed, so it is not chained). A lagging but not stale mirror stays selectable and shows a warning. Accepted trade-off: a slow mirror with the exact reference `Date` ranks above a much faster one that is one signing generation (about 6 hours) behind. `--verbose` must show the actual mirror AS (or `unknown`) and same-AS status (`same`, `diff`, or `unknown`) so a reader can understand and audit the AS tie-break; the default report shows neither (Output), and no output may imply AS preference when the lookup failed.
10. **Plan and write**: build the plan described in Apply, validate it against the closed target enumeration and the current on-disk digests, and only then write. A run that may not write stops after the recommendation. No step of this is user-visible or separately invocable.

## TUI

Library: `ratatui` + `crossterm` (no async). Opens only with `--tui`, after probing finishes (a progress view is shown while probing).

- Layout: ranked mirror table (left/top), a detail panel for the highlighted mirror, and a footer with the active keys.
- Table columns: checkbox, rank, host, country, scheme, latency, throughput, lag (updates), AS match, signature, `Recommended` badge.
- Detail panel: full URL, country, AS number and name, resolved IP, scheme, time to first byte, throughput, `Date` and lag for `-updates` (decides) and `-security` (informational), AS match, signature status of the `-updates` `InRelease`, mirror list source, status or rejection reason.
- Recommendation: the best-ranked mirror is pre-checked and carries the `Recommended` badge. Rejected mirrors are shown dimmed, with the reason, and cannot be checked.
- Selection: multiple checkboxes. The first checked mirror in rank order is the primary (active URI); other checked mirrors are written as commented `alternative` lines (see Apply).
- Keys (arrows are primary; `j/k` not required):
  - `Up`/`Down`: move in the focused section. `Left`/`Right`: switch tab/page within a section (e.g. the `-updates` and `-security` detail tabs) or collapse/expand details.
  - `Tab`/`Shift+Tab`: cycle focus between sections (mirror table, detail panel, buttons).
  - `Space`: toggle checkbox on the highlighted mirror.
  - `Enter`: confirm the current step or dialog (accept, yes).
  - `Esc`: cancel the current action or close a dialog; on the main screen, quit without changes (asks to confirm if the selection was changed).
  - `Insert` (implemented in the last milestone): add an entry: opens an input dialog for a custom mirror URL (validated, then probed like any candidate and added to the table).
  - `Delete`/`Del` (last milestone): remove the highlighted entry from the list (asks to confirm; only affects the current run, never apt files).
  - `r`: re-probe. `?`: help.
- Zero-effort flow: defaults must be right, so pressing `Enter` through the flow saves the best fresh mirror among the existing candidates. Keep the step count minimal, but never hide information the user needs. Base path (3 steps):
  1. Mirror table with the `Recommended` mirror pre-checked and a one-line summary of what will change; `Enter` continues.
  2. Confirmation dialog `Apply changes? [Yes]`: lists the files to change, old URI -> new URI, alternatives, and the backup path; `Yes` focused. As root, `Enter` validates the plan and writes it, so the dialog is the confirmation and `--yes` is not needed. As a non-root uid, `Enter` prints the one line `sudo apt-scout --tui` and exits 3; the TUI writes nothing.
  3. Result screen: as root, `applied <mirror> to <files>`, the backup path the write created, how to undo (`--restore`), and the suggested `apt update`; as a non-root uid, `nothing written, run sudo apt-scout --tui`, the files the write would change and the backup path it would create. `Enter` exits.
- Extra steps appear only when the user must be informed or decide: selection has warnings (e.g. only http, lag near `MAX_LAG`, different country), a custom mirror failed its probe, no fresh mirror found, the write failed (show the reason and the state of the backup, which is untouched).
- Every dialog shows its available keys in a footer bar.
- Applying from the TUI uses the same writer as the default run: as root, `Enter` on the confirmation validates the plan and writes it; as a non-root uid the TUI writes nothing and prints the `sudo apt-scout --tui` line. Every other Apply rule below holds unchanged.
- Terminal state is always restored on exit, panic or Ctrl-C.

## Apply

- One code path writes, and it is internal. Discovery, verification, rewrite planning and confirmation produce a plan; the plan is validated against the closed target enumeration and the current on-disk state; only then does the first byte change. The plan is never a file, never a message on stdin, and never a flag: the user does not type a step of it, and it does not cross a process boundary. It names files through a fixed enumeration and carries the selected mirror, the verification result that authorizes writing it, the exact bytes, mode, and owner of every file it was computed from, and the exact bytes to write. It carries no freshness baseline of its own: the caller establishes one from the canonical reference when that reference has a verified `-updates` `Date` read inside the signed region, otherwise from the newest candidate in this run that carries one, after the clock-skew sanity guard of step 8, and the writer holds the selected mirror's proof against it before the first byte, refusing outright when no verified baseline was supplied, because a writer that may not fetch cannot establish one. The write aborts, before its first byte, on any missing field, any mismatch with the file on disk, any digest it cannot recompute to the same value, any target that is not a regular file after resolution, and any plan it did not fully validate. The plan binds to the disk by comparing those bytes, not by a hash; every digest the manifest records is SHA-256 over the exact bytes it describes. The write performs no network request of its own, invokes no shell, resolves no command through `PATH`, and reads no environment variable. Never write without root. The confirmation prompt is a safety rail, not a security control: the guarantee is the validation, and `--yes` removes only the prompt. A `--restore` plan is authorized by the backup it was re-derived from instead of by a verified mirror: it carries no selected mirror and no baseline, the baseline rule above is a mirror's rule, and every other requirement in this bullet applies to it unchanged.
- Source discovery and inventory are read-only. Scan `/etc/apt/sources.list` and regular `*.list` / `*.sources` entries under `/etc/apt/sources.list.d/`; do not follow symlinks. Report each inspected file and each skipped file/stanza/URI with its reason before mirror probing. If no eligible official archive URI exists, stop before reference/mirror probes: `--list` exits 0, a non-root run prints the `sudo` line and exits 3, and a root run that was going to write exits 1. D7 extracts URI tokens and suites only; it performs no writes.
- Rewrite per URI token, not per file or line. Rewrite a URI when its host is `archive.ubuntu.com`, `*.archive.ubuntu.com`, or a host and path the Launchpad mirror list names in any country, not only the run's own country, so a mirror this tool wrote stays rewritable after the operator changes country: otherwise a choice the tool made can be undone only by hand, which the run that made it must not leave behind. Membership answers recognizability, not trust: it makes an existing URI eligible for replacement and nothing else — the replacement is still the selected candidate, validated and with its `-updates` `InRelease` verified per probe, and the list source is trusted no further than it already was. Eligibility is by the listed URL's host and path, not by the host alone: an on-disk URI token is eligible only when its host matches a listed mirror's host and its path begins with that listed entry's path, compared by whole segments, so a listed `/ubuntu` admits `/ubuntu/` and `/ubuntu/dists/...` but not `/ubuntufoo`. A mirror host usually carries several trees and only the Ubuntu tree is what this tool may replace: `deb http://ftp.uni-stuttgart.de/debian trixie main` is left alone even when that host is listed as an Ubuntu mirror at `/pub/linux/debian/ubuntu/`. A listed entry whose path is `/` admits every path on that host, because the list names no narrower tree there and the tool cannot tell the trees apart; that is acknowledged rather than hidden, and it is why the canonical archive and its `*.archive.ubuntu.com` names stay recognized at any path. A dot segment is never eligible and never enters the set: a token whose path carries `.`, `..`, or the `%2e` spelling of either is left unchanged with a reason naming the segment, and a listed entry whose path carries one is dropped and reported, so neither the any-path rule above nor a listed prefix can admit a path that traversal would resolve elsewhere. The test is lexical: nothing is decoded or resolved, so `%252e` is a literal segment name and `...` is an ordinary segment. The port is not part of the comparison, as before. `--https-only` does not narrow what is recognizable: a mirror written over `http` stays recognizable in a later `--https-only` run. Every entry of every list source passes the same candidate URL validation before it may enter the set, the Launchpad page and the `mirrors.ubuntu.com` fallback alike, and an entry that fails is reported and left out, never silently trusted. Launchpad is the only list that names every country; `mirrors.ubuntu.com` is read one country at a time (`<CC>.txt`) and its `mirrors.txt` names only the canonical archive, so outside Launchpad the eligible hosts and paths are the ones in the file the run did load and an entry outside it is reported as skipped rather than rewritten. The set therefore fails closed in the only direction open to it, shrinking and never widening, and when no URI is eligible the run stops under the no-eligible-URI rule and touches nothing. A path prefix is a recognition rule and its cost is stated here rather than discovered later: when a host is listed at a path other than the one an on-disk URI carries — a listing that changed its layout, or an entry since delisted — that URI is reported as skipped with its reason and left unchanged, not forced through. Never rewrite `security.ubuntu.com`, `ports.ubuntu.com`, `ppa.launchpad.net`, `ppa.launchpadcontent.net`, or any host under `launchpad.net` or `launchpadcontent.net`: that refusal list is explicit and is checked before any membership test, whatever a list names. Naming those hosts is the point: before this rule a PPA was safe only because no list happened to name a PPA host, which is not a control. A line or stanza whose suites include a `-security` suite is never rewritten to a probed mirror, even when its host is `archive.ubuntu.com`, because `-security` freshness is not checked; report each skipped entry and why. The only exception is the Pop!_OS split above, which keeps `-security` on the original mirror. On Ubuntu 24.04 and later security already lives in its own stanza (`security.ubuntu.com`), so no split is needed.
- deb822 (`/etc/apt/sources.list.d/*.sources`): a stanza's `URIs:` field may hold several URIs; D7 recognizes continuation lines, repeated fields, comments and stanza boundaries; rewrite only matching tokens in later milestones. Keep every other field (`Types`, `Suites`, `Components`, `Signed-By`, ...) and comments byte for byte. Do not touch stanzas with `Enabled: no`. Missing or malformed `URIs`/`Suites`, duplicate singleton fields, and unknown formats are reported and never guessed.
- Legacy (`/etc/apt/sources.list`, `*.list`): D7 recognizes `deb`/`deb-src` lines, bracketed options such as `[arch=... signed-by=...]`, comments and URI tokens; rewrite only the URI token in later milestones. Malformed lines and unsupported URI schemes are reported and never guessed.
- `mirror://` / `mirror+file:` URIs (older installs): leave unchanged and report them with an explanation.
- Alternatives: in the TUI, the first checked mirror in rank order becomes the active URI. Other checked mirrors are written as commented lines `# alternative: <uri>` above the changed line, so the user can switch quickly. apt has no failover across URIs, so alternatives are documentation only.
- Safety checks before writing: target is a regular file (do not follow symlinks), keep mode and owner, no half-written files.
- File creation is planned, never incidental: `/etc/apt/sources.list.d/system-security.sources` is created with `create_new` and mode 0600, and `EEXIST` aborts the whole apply with nothing written. A planned write that creates a file is accepted only when the platform is Pop!_OS and the target is exactly `sources.list.d/system-security.sources`; a plan that creates any other file, or replaces a file that does not exist, aborts before the first open.
- Backup every file to be changed to `/var/backups/apt-scout/<UTC timestamp>/`, directory mode 0700, refuse a symlinked directory. Write a manifest of original paths. Abort the whole apply if any backup fails.
- Write atomically: temp file in the same directory, fsync, rename.
- `--restore` copies the newest backup back, in one root run: it reads `/var/backups/apt-scout/<backup id>/MANIFEST` itself and aborts before parsing a byte unless that path is a regular file, owned by root, mode 0600, and not a symlink. It then re-derives the target set and every per-target digest from the manifest itself and validates them: every entry matched to the closed target enumeration, every path under `/etc/apt/`, a regular file after resolution, and every recorded digest, mode and owner matching the backup copy it names, refusing the whole restore on the first disagreement; a file the run created has no backup copy, so its record carries the digest, mode and owner the run created it with, and the restore refuses to remove it unless the file on disk still matches. The manifest is the source of truth for what is written, not a list of files the run already chose, so a stale or partial manifest cannot apply a subset of the backup. `--restore` does not depend on the rewrite logic, and it reaches the writer through the same validation as an apply. It is executed by that same writer, through the one entry point the writer has: the restore engine re-derives the plan and hands it over with no baseline, so a restore adds no second write path and no write code of its own. The newest backup is the greatest id under `/var/backups/apt-scout/`, because the ids are zero-padded UTC timestamps and their string order is their age; it is the only backup a run considers, so a restore whose newest manifest or copy is refused fails as a whole and never falls back to an older backup, and a backup root that holds no id, or an id whose directory is not a plain directory, is a failure that writes nothing and exits 1. A restore is itself a write and backs up every file it replaces or removes under its own id, exactly as an apply does, so after one restore the newest backup is that restore's; the file it removed is one of them, recorded there as a file to put back with the bytes it held and with a copy beside it, so what refuses a second restore from that backup is the disk rather than the manifest — the record says replace and the target is gone — which is the record-versus-disk rule above rather than a guess.
- Custom URLs (`Insert`): scheme `http` or `https` only; reject userinfo, whitespace, `file:`, and loopback/private/link-local addresses; probe like any candidate; show a warning before apt is pointed at a user-supplied host.
- If no URI is rewritable (for example arm64, or a system already using a third-party mirror), say so before any probing: scan the sources first, print every file inspected and why each entry was skipped. `--list` exits 0, a non-root run prints the `sudo` line and exits 3, and a root run that was going to write exits 1. Do not probe 30 mirrors for nothing.
- Candidate hygiene (mirror lists are partly fetched over plain HTTP): every candidate, from any list source, must be `http`/`https`, have no userinfo, and not resolve to a private, loopback or link-local address. Results from the `mirrors.ubuntu.com` fallback are marked unverified in the output.
- After apply, suggest `apt update`; do not run it.

## Privilege boundary and threat model

- Security goal: untrusted inputs must not let an attacker execute code as root or write outside the explicitly allowed apt paths through apt-scout.
- Treat CLI arguments/environment, apt source contents, network responses, mirror URLs, backup manifests, file metadata/races, and terminal input as untrusted.
- One process writes, and the accepted cost is stated here rather than hidden. In a root run the networked discovery and the parsing of untrusted responses — geolocation, mirror lists, `InRelease` bodies — happen in the same root process that later writes, because that is the workflow the user chose when running `sudo apt-scout`. What defends the user is the order of operations: nothing is written until the selected mirror's `InRelease` verifies and the internal plan validates against the on-disk state. A two-process split that keeps the network phase out of root is future work and is not a supported flag in v1.
- The write path must use fixed executables/paths and a minimal controlled environment; it must not invoke a shell and must not resolve a command through `PATH`, and after verification it spawns no external process. Validate file type, ownership/mode policy, path containment, and symlink/TOCTOU behavior at the point of use; fail closed on any mismatch.
- The program never re-execs itself privileged, never invokes `sudo`, and is never installed setuid. Privilege is obtained only by the user running the program as root. A root run is the same binary with the same code; the only thing that changes is that it may write. Security review reduces risk but is not a guarantee of absolute immunity.
- What a write is bound to: the bytes it writes are the bytes its own validation passed, over a disk state that still matches the digests it computed. Every target's new content carries a digest the writer recomputes, and a mismatch is refused. The confirmation prompt is a safety rail, not a security control: the guarantee is the validation, and `--yes` removes only the prompt.
- The writer is one code path in one binary, shared by the default run, the TUI confirm, and `--restore`. A separate privileged artifact is out of scope for v1, as is a two-process split; either would be a new product decision, not something a size measurement or a code review finding can trigger.
- Before D9 or any write implementation, D6c, D6e, and D6f must be complete. Every write PR needs a security-focused exact-diff review and disposable Ubuntu-container tests for path traversal, malformed manifests, symlinks/races, backup failures without partial writes, rollback, and rejection of paths outside `/etc/apt`. Never run write tests on the developer host.

## Resilience

Third-party services change formats, add limits or become paid. The program must keep working when they do.

- Geolocation and AS lookups are optional. If country detection fails, the program asks for `--country`, or runs with `--any`; it never silently guesses a worldwide list, and the one widening Pipeline 4 describes is announced, refused when the loaded list names one country, and never a substitute for a detected country. If AS lookup fails, ranking proceeds without AS preference. Failures include source and reason.
- Core data comes from sources the project depends on anyway: the Ubuntu archive (`InRelease`), Launchpad mirror list, DNS. No account, key or paid tier is needed anywhere.
- Parsers reject unexpected shapes instead of guessing, and report which field was missing.
- Weekly contract check (`.github/workflows/source-contract.yml` runs `.github/scripts/check-sources.sh`; the script can be run locally; not a required check): fetch each live source once, check that the fields the parser needs are still present, and open an issue only after two consecutive failures (runner IPs can be rate limited by individual services). Scheduled workflows on public repos are disabled after 60 days without repository activity; the check is advisory.

## Errors and self-healing

Principle: the program solves its own problems when safe, and otherwise says exactly what happened, where, why, and what to do. Vague messages ("Unknown error", "Something went wrong", bare `No such file`) are forbidden.

- Every error message states: **what** failed, **which path/URL/value**, **why** (the underlying OS or HTTP error, kept verbatim), and **how to fix** it. Example: `Cannot write /var/backups/apt-scout/: permission denied (os error 13). The path is not writable even as root, which means a read-only mount or an immutable attribute; nothing was written.`
- Error types carry context at the failure point (path, URL, step name); never discard the source error. No `unwrap()` on IO or parsing.
- Self-heal automatically (and tell the user in one line what was done):
  - Missing own cache directory: create with `create_dir_all`. `/var/backups/apt-scout` is created by the writer and verified after creation to be a directory, owned by root, mode 0700, and not a symlink; a pre-existing path that fails any of these is a hard abort with nothing written.
  - Missing, empty or corrupt cache file: ignore it, refetch, rewrite it.
  - Missing `/etc/os-release`: try `/usr/lib/os-release`, then `lsb_release` fallbacks; if still unknown, ask for `--codename`/`--distro` flags.
  - Missing `UBUNTU_CODENAME` and `VERSION_CODENAME`: use the codename in the existing apt sources, then ask for `--codename`.
  - Apt sources at an unexpected location or format: search `/etc/apt/sources.list`, `/etc/apt/sources.list.d/*.{list,sources}`, and report every file inspected and why each was skipped or used.
  - Network failure: follow the mirror-list source chain, retry, then use cache/snapshot; report each failed source with its reason.
  - Interrupted write: temp files are cleaned up on the next run; the original file is never left half-written.
- Do not self-heal when it is unsafe: never guess which apt file to overwrite, never continue after a failed backup, and self-healing never creates a file in `/etc/apt`. That last prohibition is about self-healing, not about planned writes: the only file apt-scout ever creates there is the planned `sources.list.d/system-security.sources` on Pop!_OS (see Apply), which comes from the validated plan and is opened with `create_new`. Stop and explain instead.
- No silent data-source fallbacks: whenever a fallback is used, print which one and why. Message text falling back to English is not a data-source fallback and is not announced (see Localization).
- Exit codes (see Non-functional) always accompany a message that explains the cause.
- Tests cover the message content for the common failures (missing dir, permission denied, corrupt cache, unreachable network, unknown distro).
- Docker integration tests for source discovery/apply/restore must use disposable Ubuntu containers and isolated `/etc/apt` fixtures. Never mount or mutate the developer host's `/etc/apt`; test rollback, manifest path validation, permissions, and byte-exact restore in the container. Write tests cover: a non-root run writing nothing and exiting 3, a root write aborting before its first byte on a failed validation, symlinked targets and a symlinked `sources.list.d`, substitution between validation and write, a target whose recomputed digest does not match the bytes to be written, a restore whose manifest is stale, partial, or names a path outside `/etc/apt`, a read-only `/etc/apt`, backup failure aborting before any write, byte-exact restore of content/mode/owner, hostile `PATH`/`HOME`/`TMPDIR`, a pre-existing `system-security.sources` aborting the apply, and a write that still succeeds when `/usr/bin/gpgv` is removed after verification has already happened (test hook), proving the write does not re-verify.

- Security note: all geolocation and AS answers are untrusted input, validated, and influence ranking only. Canonical's lookup is plain HTTP; AS data comes from DNS. Nothing derived from them is ever written into apt sources.
- Freshness trust boundary: ranking may display and use an `InRelease` `Date` even when signature verification is `invalid` or `unavailable`; this can mis-rank a mirror but cannot authorize package installation. Every `-updates` `InRelease` used by probing is verified with `/usr/bin/gpgv --keyring /usr/share/keyrings/ubuntu-archive-keyring.gpg`, using no shell, no `PATH` lookup, a cleared environment, a private 0700 temporary directory that is also `gpgv`'s `--homedir` (so no user GnuPG configuration or default home can influence the result), a 10-second process timeout, and a 1 MiB cap on captured status output. The download cap is the verifier's own 512 KiB cap, so an oversized file is rejected at download instead of being reported as an unverifiable but rankable mirror. The informational `-security` pocket is read as a ranged head of 4 KiB and is never verified, because nothing consumes its signature. Missing/invalid `gpgv` or keyring, unsigned/changed/unknown-key data, oversize data, and execution errors are shown explicitly and are never `Verified`. Only a `Date` from inside the cleartext-signed region (step 8) is ever trusted: bytes before `-----BEGIN PGP SIGNED MESSAGE-----` or after `-----BEGIN PGP SIGNATURE-----` are outside what `gpgv` signs, so a `Date` read there is shown and ranked, is never a verified date and never authorizes a write. Ranking may use a `Date` whose status is `invalid` or `unavailable`, but only a `Verified` `Date` parsed inside the signed region is usable by a write. Before a write may use a ranked mirror, the selected mirror's `-updates` `InRelease` and the write baseline must both be `Verified`. Ranking has a separate baseline that ignores verification and may fall back to the newest candidate `Date`, verified or not. The write baseline may not ignore verification: it is the canonical reference when that reference's own `verified_updates` field is `Some`, and otherwise the newest candidate whose own `verified_updates` field is `Some`; when neither the canonical reference nor any candidate yields one, a write fails closed. Trusted freshness dates are represented by a value that only a `Verified` status can construct (`VerifiedDate`), and the probe result, the reference and the ranked entry each expose it, so a write path takes that value and never a bare `Date`. If verification is not available, write mode fails closed while read-only ranking still works. `VerifiedDate` protects the date half only: it wraps a `fresh::SignedDate`, which only the strict in-region parser builds, so no write path can be handed a `Date` read outside the signed region. The status half is protected the same way: `SignatureStatus::Verified` carries a `VerifiedProof` whose single field is private and which only the verifier's `GOODSIG`+`VALIDSIG`+exit-0 path can mint, and that proof carries the date it read inside the region it verified — so a caller can neither forge the status nor pair its own date with a genuine proof. `ROADMAP.md` task D25 records the change that closed both halves before the writer was wired in. `.deb` packages must depend on `gpgv` and `ubuntu-keyring`; tarball instructions must name them.

## Localization

- **Display text only.** A locale selects the words a run prints and nothing else. It is never an input to a path, a filename, a decision, a comparison, an ordering, the plan, the bytes written or an exit code, and the privileged path never reads it: the locale is resolved once at startup, before any apt file is opened, and no module reached from `src/apply.rs` reads an environment variable. `LC_ALL` and `LANG` choose the words a run prints. With `NO_COLOR`, which only turns colour off (Output), they are the only environment reads that can influence printed text: no other read can change a character a run prints, and none of the three reaches a decision, a path, a byte written or an exit code. `TMPDIR` is the only other environment variable the shipped binary reads — through `std::env::temp_dir()` in `src/verify.rs`, for the verifier's private 0700 directory — and it selects where that directory lives and nothing else: it reaches no decision, no `/etc/apt` path and no byte written, and a value that names no usable directory makes verification unavailable and a write fail closed. Two runs that differ only in locale print different text, write identical bytes and exit with the same code.
- **English is the default and the fallback.** Every user-facing message has an English text. A run whose locale the binary does not carry prints English; a message the selected catalog lacks prints its whole English text, never a blank and never a half-translated line. The unit of fallback is the message, not the fragment.
- **Message ids are stable and are never keyed on English text.** A message is addressed by a table key naming its role — `rejected_stale`, `table_header_signature` — matching `^[a-z][a-z0-9_]*$`: lowercase ASCII letters and digits joined by `_`, starting with a letter. The pattern is written anchored, and that is part of the requirement rather than notation: an unanchored `[a-z][a-z0-9_]*` matches an id-shaped run anywhere in a longer name and accepts `rejected.stale`, so the test states the anchored literal and asserts that the dotted name is rejected. The id space is the catalog format's, not the crate's module layout: a Fluent message id is `[a-zA-Z][a-zA-Z0-9_-]*` and a `.` there is attribute access, never part of an id, so a dotted name such as `rejected.stale` is not a message id any loader accepts, and the pattern above is a deliberate strict subset of the ids it does. An id never changes when its English sentence is rewritten: no id contains a space, so no id can be an English sentence, and editing English invalidates no translation.
- **Selection is RFC 4647 lookup.** `LC_ALL` when set and non-empty, else `LANG`, else English. No other environment variable, no option and no configuration file selects a locale: `LANGUAGE` and `LC_MESSAGES` are deliberately not read. The value is normalized to a language tag first — charset and modifier dropped, `_` written as `-`, `lt_LT.UTF-8` becomes `lt-LT` — and then matched against the shipped tags by lookup: the exact tag, else the language alone, else English. So `lt_LT.UTF-8` selects the `lt` catalog, and `de_AT.UTF-8` and `de_CH.UTF-8` both select `de`. A value that is not a language tag (`C`, `POSIX`, empty, unset) selects English without an error, and the program prints UTF-8 whatever the charset suffix claims.
- **Chinese is selected by script, before the lookup, and a script is never substituted.** `zh_CN`, `zh_SG`, `zh_Hans_*` and bare `zh` select Simplified (`zh-Hans`); `zh_TW`, `zh_HK`, `zh_MO` and `zh_Hant_*` select Traditional (`zh-Hant`), which v1 does not carry, so those runs print English rather than Simplified. Script subtags are the only place the region decides the tag, because a plain lookup cannot tell Simplified from Traditional. The same rule applies everywhere: a locale the binary does not carry, including Norwegian Nynorsk (`nn`), prints English.
- **The catalogs are Fluent files compiled into the binary.** Each locale is one `locales/<tag>/main.ftl`, and `locales/en/main.ftl` is the source of truth every other catalog is translated from. `src/l10n.rs` builds them with `fluent-templates`' `static_loader!` and English as the fallback language, so the catalogs are compiled at build time: nothing is read from the filesystem at run time, no locale path comes from the environment, the release is still one static musl binary, and the shipped set is the set of directories under `locales/`.
- **The dependency set changes once, by decision, and `cargo deny check` is what approves it.** `fluent-templates` 0.15.1 and the crates it resolves to — `fluent-bundle`, `fluent-syntax`, `fluent-langneg`, `unic-langid`, `intl-memoizer`, `intl_pluralrules`, `self_cell`, `rustc-hash`, `type-map`, `smallvec`, `displaydoc`, `thiserror`, and the proc-macro crates `fluent-template-macros`, `syn`, `quote`, `proc-macro2`, `proc-macro-hack` and `unicode-ident` that build the loader and never link into the binary — are MIT OR Apache-2.0, a disjunction containing one of them, MIT alone, `Unlicense OR MIT`, `Apache-2.0 OR GPL-2.0-only`, `Unicode-3.0` for the ICU `tinystr`/`zerovec`/`zerofrom` crates, or `(MIT OR Apache-2.0) AND Unicode-3.0` for `unicode-ident`. `deny.toml`'s allow-list already covers every licence in that set and does not change; `cargo deny check` must stay green in the PR that adds the dependency, and that PR lists the resolved set with its licences. This is the crate's second dependency family and it is taken deliberately: one dependency is the default, not a prohibition, and a dependency enters by an explicit licence-checked decision rather than by accident.
- **A catalog is complete or it is not shipped.** For every shipped locale the test suite requires every English message id, the same placeholder set in every message as its English entry, and every plural category that language's CLDR rule can return; a gap fails `cargo test` with the list of missing ids, not the run, and that list is the work queue a translator starts from; the gate's own report is tested too, against a fixture catalog with one known id removed, so the failure text a translator works from is checked rather than assumed. Every message also carries a `#` comment above it naming when it is printed and what each placeholder holds, and a message without one fails `cargo test`: the comment is what a translator reads, so a bare placeholder whose meaning is nowhere written is a defect. Translated text lives only in the catalog files: a translated string never appears in `src/`, in the documentation or in a test.
- **A catalog that does not parse cannot ship.** The tests parse every `locales/*/main.ftl` and fail with the file and position of the first error, and `cargo test` also forces the compiled catalogs to load, so a catalog the binary carries and cannot parse is a test failure. A missing message id in a release binary prints a visible lookup diagnostic rather than nothing, and no lookup can change a decision.
- **Plurals and numbers.** A counted message is one Fluent message with a select expression over the counted variable, and the plural category is chosen by the library from the catalog's own language; the crate carries no plural rule of its own. Numbers, byte counts, dates and durations are formatted identically in every locale, with ASCII digits and ISO 8601 dates; only the surrounding words are translated.
- **Never translated.** Mirror hostnames, URIs, package names, file paths, option names, country codes, AS numbers, the program name and the `sudo apt-scout ...` line a non-root run prints: a user copies that line, so it stays runnable. Prompt answers (`y`, `yes`, `n`, `no`, and empty for the default) are not translated either; only the question is. A printed message carries no character the user cannot see: Fluent's Unicode isolating marks around placeholders are disabled, so a copied URI is the URI.
- **Column alignment counts display columns, not characters**, so a double-width script lines up in the ranked table like a Latin one. The width function is the crate's own, tested against a fixture table of code points whose East Asian Width is known, and the ranked table is padded with it rather than with a character count. Nothing is claimed for emoji, for combining sequences outside the listed ranges, or for right-to-left text.
- **Ordering never uses translated text.** Where a run sorts, the key is a mirror URL, a message id or another value that is identical in every locale. A rejection carries its message id and its arguments and is rendered when it is printed, so no order can depend on the locale a run happens to print in.
- **Manuals.** The English page is the only one every release must carry. A locale that carries a catalog is owed its own page at `man/<locale>/man1/apt-scout.1`, installed to `/usr/share/man/<locale>/man1/`, where `<locale>` is the system name man-db resolves: `lt`, and `zh_CN` for the `zh-Hans` catalog, because man-db looks up a locale name and not a script tag. The page follows its catalog instead of leading it, so no release owes a page for a locale it does not carry: `ROADMAP.md` D33 delivers the first two, `lt` and `zh_CN`, after D31a and D32, and every locale added later ships its page in the PR that adds its catalog, under the same check. A page documents the same behavior and is checked with `mandoc -Tlint` and `man -L <locale> apt-scout` in a container. Its examples match that locale's `--help`, whose text comes from the catalog; `--help` is never a second document that can drift from it.

## Testing

- Unit tests (`#[cfg(test)]`) cover pure logic on fixtures: `os-release`, Launchpad HTML, `mirrors.txt`, `InRelease` dates, freshness, ranking, read-only apt source inventory/parsers, and D8 source rewrite output/round trips. Saved fixtures come from real responses (the Launchpad page is ~316 KB; keep a trimmed copy with at least two countries and every status value seen).
- Docker integration tests run inside disposable real Ubuntu images; offline cases and live-network smoke cases are both included. Live cases require internet and are manual, never part of CI. The matrix covers every supported release; format measured on 2026-11-11:

  | Release | Codename | Sources format |
  | --- | --- | --- |
  | 20.04 | focal | legacy `/etc/apt/sources.list` (10 `deb` lines) |
  | 22.04 | jammy | legacy `/etc/apt/sources.list` |
  | 24.04 | noble | deb822 `/etc/apt/sources.list.d/ubuntu.sources` |
  | 26.04 | resolute | deb822 `/etc/apt/sources.list.d/ubuntu.sources` |

  Fixtures for verification live in `tests/fixtures/signed/`: the real `noble-updates` `InRelease`, a tampered copy of it, and the Ubuntu archive keyring. A forged body is built in the test from the signed fixture by prefixing a `Date:` line, so the regression proves all three facts at once: the prefix verifies under `gpgv`, the signed-region parse yields no date for it, and read-only ranking still uses the displayed date. Unit tests that need a real `gpgv` and keyring skip when `/usr/bin/gpgv` or the archive keyring is absent (developer hosts), and the Docker cases are the end-to-end proof of the positive path. Releases whose reference `InRelease` returns 404 are handled by the exit-4 rule in step 8. `focal-updates` was still receiving updates on 2026-11-11 (`Date` 2026-11-11), so freshness stays meaningful for 20.04; keep a focal fixture. `i386` is in scope but covered by fixtures only (no i386 image). The `amd64` images are used (`--platform linux/amd64`); on Apple Silicon they run under emulation, slower but equivalent. Current Docker tests cover distro detection, read-only inventory/early stop, live mirror ranking, the missing-`gpgv` case (every signature reads `unavailable (<reason>)` while ranking and the exit code stay usable), one live case that requires a real `verified` reference and at least one `verified` mirror row after installing the two `.deb` dependencies, because a base image is not a package install, and the restore cases W27–W33, which reach the flag the user types against a backup a real write made, including the interactive confirmation answered both ways. Later source-write milestones must test rewrite, backup, atomic write, `--restore` and error messages inside disposable containers with isolated `/etc/apt`; the restore cases are W27–W33 in `scripts/docker-test.sh` (a positive restore after a real write, a second restore refused, a non-root run that opens no backup, a tampered copy, a target replaced behind the backup's back, and the confirmation answered `y` and `n` on standard input). Network answers in automated tests are otherwise injected from fixtures.
- Localization is tested in two layers, and a catalog ships only when both pass. In-process, over the files the binary carries: every `locales/*/main.ftl` parses (a failure names the file and position), the compiled catalogs load, the shipped set the binary reports equals the set of locale directories, every English message id exists in every shipped locale with the missing ids listed on failure, placeholder parity per message, a `#` comment on every message, every plural category the language's CLDR rule can return, the mapping table (`lt_LT.UTF-8` to `lt`, `de_AT.UTF-8` to `de`, `zh_CN.UTF-8` to `zh-Hans`, `zh_TW.UTF-8` to English, `zh_Hans_*` and `zh_Hant_*` by script, `C`, `POSIX`, empty and unset to English, an unshipped language to English), the width function against its fixture table, and the literal gate that refuses a printed sentence outside `src/l10n.rs`. The completeness gate's discriminating power over English-tied ids is shown in the same layer: from the first translated catalog on, renaming one English id must fail the completeness gate for every shipped locale other than English, naming the id as missing. In a container: the read-only CLI and a root write run each executed twice against the same fixture image, once under `LANG=C` and once under a shipped locale, compared on exactly four things — the exit code, the bytes of the container-local `/etc/apt` tree, the backup manifest's bytes for the write pair, and the harness tokens — with the printed display text the only thing allowed to differ. The root pair is the write path's evidence; the read-only pair says nothing about it. A pair whose two runs print the same text is two copies of one run — with English as the only shipped catalog it passes whatever the write path reads — so the pair discriminates only from the first translated catalog on, whose own entry carries the same four comparisons and requires the translated run to print that locale's text. Neither pair is claimed to cover a path its fixture does not reach.
- One script (`scripts/docker-test.sh`) runs the container tests on the developer's machine only; CI does not run Docker tests (CI builds and runs static checks). The write cases run against the container's own `/etc/apt`, with no path override of any kind: there is no runtime override, because the writer reads no environment variable, and, once those cases land, the write entry point they use must exist only in a build compiled with the test-only `apt_scout_write_harness` cfg, which `scripts/docker-test.sh` must set with a build flag passed to that crate's own compilation when it builds that binary and which no release build may set. Run it before opening a PR that changes `.rs` files or build configuration, and state the result in the PR. TUI milestone additionally requires a laptop launch against safe fixture/mock data for user visual inspection, followed by runtime checks in local Ubuntu Docker emulation; visual acceptance requires explicit user confirmation.
- Pop!_OS is tested in an Ubuntu 22.04 container with the real `pop-default-settings` package downloaded from `apt.pop-os.org` (pinned by file checksum in the test fixtures, downloaded once and cached; the download is a test setup step, not a test of the live service): its `os-release` and the deb822 `system.sources` template from its `postinst` are the fixture. Linux Mint is covered by its documented `os-release` (`ID=linuxmint`, `VERSION_CODENAME=wilma`, `UBUNTU_CODENAME=noble`) in a container. Neither is a full installation, only the files this tool reads and writes.
- Live-network smoke tests (real Launchpad, geo sources) are manual, never part of CI, because they are rate limited and flaky.
- Man-page verification checks `man/apt-scout.1` formatting (for example with `mandoc -Tlint`) and confirms `man apt-scout` renders in a disposable Ubuntu container. Every example must match `--help` and the implemented CLI; do not document planned flags as available.
